# Express arithmetic: number formats, quantisation and the RE3 hand-off

What the shipped GE7 and HQ2 microcode and the published Elan report settle about the arithmetic of the Express pipeline, for an emulator author who wants to rate a model against the board: the GE7 number format, how colour is quantised, the fixed-point words the geometry engines hand to the raster engine, and the mode words that state tokens write into it. What the evidence does not reach is listed as unknown, with the route that would settle it. Companion pages: [microcode.md](microcode.md) (instruction decode), [pipeline.md](pipeline.md) (token catalogue), [host-contract.md](host-contract.md) (host-visible flow control), [devices/re3](../../devices/re3/README.md), [devices/ge7](../../devices/ge7/README.md).

Ratings are the repository's three: **established** (read in full from a binary or a published document), **inferred** (a reading checked against known behaviour, reasoning given) and **unknown**. Tags: `[public]` the Elan Graphics Technical Report ("TR"), `[binary]` a shipped binary, cited by install path, routine and microstore address (a software expectation, not a hardware measurement). No upstream header, no MAME or iris register name and nothing from the IRIX source tree was used: those carry hypotheses, not evidence, and the names iris uses for RE3 operations are not repeated here.

## Sources and how to reproduce

- `usr/gfx/ucode/ge7.bin` (IRIX 6.5 base media, 611432 bytes, SHA-256 `085d9e92...4729`) and `hq2.bin` (`0c1fbe18...fc94`); addresses below are GE7 microstore addresses ("GE7 n"). Known answers come from the diagnostic program `ide.IP20` (Diagnostics 5.2, `744fdebc...df14`, [binaries.md](../../references/binaries.md)) and the 4.0.5D console images. The 6.5 base `ide.IP20` (`5ede622e...`) has none of the known-answer test symbols, so it is not a source for them.
- Host-side encodings come from the n32 `libGLcore.so` that [binaries.md](../../references/binaries.md) records under `usr/gfx/arch/IP12GR232` (SHA-256 `b6731da1...`). No copy with that hash was located: the 6.5 base file at that path hashes to `8dd07de0...` and was not read. Every host-side claim on this page is therefore inferred (source build not located).
- Every microcode claim is reproducible with [tools/ge7-step.py](../../tools/ge7-step.py): `run IMG START --slot N=V,.. --unknown-lines low` runs one engine on the operands given and prints the RE3 writes (`selftest` checks the cases quoted here). `--unknown-lines` assumes a flag line that no known answer fixes; the mode-word probes below assume it low.
- GE7 values are read with the data-path model of [microcode.md](microcode.md#the-data-path), whose open points (selects 4 and MPYA 4, 6, 7, the store-address timing) apply: a value that depends on them is marked.

## GE7 number format

- **Layout is binary32.** The constants block decodes as single-precision values throughout: `0x3f800000` 1.0, `0x3f000000` 0.5, `0x358637bd` (the nearest single to 1e-6), `0x3f7f0000` 255/256. Established [binary] (`ucode-decode.py const IMG IDX`). The TR says the same in words: single-precision words in, a 32-bit floating-point datapath, one multiplier and one adder [public].
- **Rounding is within one unit of IEEE.** The host's `gr2_FloatOpsTest` (`ide.IP20`) sends integer and float operands (14 integers, 10 floats and their negatives) and accepts a GE7 FADD, FSUB or FMPY result when its bit pattern differs from the host FPU's by less than 2. So a model may be off by one unit in the last place from IEEE round-to-nearest, and the GE7 itself need not be exact. Established [binary] as a software expectation. Whether the hardware truncates or rounds, and what it does with denormals, infinities and NaNs: unknown. A test that would settle it: operand pairs chosen to separate truncation from round-to-nearest, run on a board.
- **Float to integer.** FIXA and FLOATA convert; the rounding of FIXA is unknown. The clamp constants in the colour path are each a few units above the largest value that must survive, which fits a truncating FIXA. Inferred.
- **Reciprocal and inverse square root.** Two 128-entry ROMs, read by 7 mantissa bits (seed) or an exponent bit and 6 mantissa bits (square root), are checked entry by entry by the host: `seed[i] = min(127, round(128 * (2 / (1 + i/128) - 1)))` and, for `i < 64`, `sqrt[i] = floor(256 * (1 / sqrt(2 * (1 + i/64)) - 1/2))`, for `i >= 64` the same without the 2, clamped to 127. Established [binary] (`ucode-decode.py roms IDE`). The routines that use them follow a seed multiply with one or two correction steps of the form `1 - x*s` (GE7 597 to 605, 4628 to 4636, 13586 to 13594; pattern read, not run numerically, because the ROM bits outside 22:16 are unknown). Inferred: Newton iteration, accurate to roughly single precision, with a few units of error.
- **Exponential table.** Constants 0 to 62 are `exp(-a i)` with a = 0.08658224285, the best fit: the largest relative deviation is 4.9e-8, and 0.0865822 gives 2.7e-6. The first entries are 1.0, 0.91706, 0.84100. The values are established [binary]; the closed form is inferred. The routines that clamp an index with `FMIN 63` or `FMIN 127`, convert with FIXA and take `x - floor(x)` (GE7 4195 to 4199, 15131 to 15134, 16692 to 16694) read a table with linear interpolation (the 127 variant at 16692 to 16694 keeps only the index). Inferred from those routines: the 63-entry table serves fog or attenuation and the 127 limit a specular or spot table; the consumer was not traced, so the EXP2-fog and spot-light arithmetic is **unknown**. What would settle it: trace the table readers from the PassFog routine (GE7 2753) and the lighting code, then compare with real-board scenes of exponential fog and local lights.

## Quantisation and colour scale

- **Clamp.** The colour channels leave the lighting code through `FMIN K[0x43]` on red, green and blue at 60 words (GE7 16705 to 20498; every use of that constant is an FMIN), where `K[0x43] = 0x3f7f0004` is 255/256 plus 4 units in the last place; the sites read are preceded by an FMAX against zero. Twelve more FMIN sites use `K[0x44] = 0x3f7ff002`, which is 4095/4096 plus 2 units (the index-mode size). Established [binary] for the constants and sites; the index-mode reading of `K[0x44]` is inferred.
- **Scale.** MakeCurrent (GE7 1628) stores either `K[0x59] = 2^19` (= 256 * 2^11) or `K[0x5a] = 2^23` (= 4096 * 2^11), and the colour routines multiply the host colour by a state word before converting. The Clear routine run on colour (0.5, 0.25, 0.5) with a scale of 2^19 writes RE3 `0x40`, `0x41`, `0x42` = `0x40000`, `0x20000`, `0x40000`, that is 128, 64, 128 shifted left 11 (`selftest`). With the clamp above this gives `floor(min(v, 255/256) * 256)` in the integer part and 11 fraction bits below it. The scale is the one value stored by MakeCurrent that turns 0 to 1 into 8 integer bits and 11 fraction bits; which store lands on state word `0xfc` depends on the store-address timing, which is open, and the other ordering would give 256/255. Inferred.
- **The margin above 255/256.** Its purpose is not shown. A clamp exactly at 255/256 converts to the same 255; the margin would keep float rounding error in earlier steps from leaving a saturated colour at 254.999 before a truncating conversion. The measured rule `min(255, floor(v * 256))` is what the clamp and a truncating conversion give. Inferred; the purpose is unknown.
- **Not settled.** Alpha scale (the fourth colour bank is written in the same order but its scale was not isolated); how RE3 uses the 11 fraction bits in 12-bit dithered modes; the colour step interval.

## RE3 iterator and register formats

- **Position.** The console routines and the pixel-DMA routines write `(v + 0x800) << 11` for x and y ([devices/re3](../../devices/re3/README.md#addresses-the-microcode-writes), known answers: the span of ten pixels at x = 100 that the host reads back). The bias flips the sign bit of a 12-bit coordinate (the microcode does it with `XOR 0x800` and a multiply by `0x800` in the X-server paths), so the integer part is a 12-bit offset-binary number and bits 10:0 hold the fraction. The 11 is established from the shift; calling bits 10:0 a fraction is inferred (the same shift is used for colour, and the mask `K[0xed] = 0xfffff800` is applied to values of this form). The y limit written at reset is `1023 << 10`, not `<< 11`, so that register has a different scale (inferred). Established [binary] for the value.
- **Colour.** 8.11, as above; index mode 12.11. Inferred.
- **Z.** The microcode compares against `K[0xeb] = 0x7fffff` and `K[0xec] = 0xff800000`, the TR's 24-bit Z buffer [public]. Reading the two constants as signed 24-bit limits is inferred. The Z and slope words are written as two-word quantities ([set-up](#set-up-and-the-hand-off)) after a conversion that multiplies by 4096, converts with FIXA, tests the magnitude against `K[0x5e]` (about 2^31) and masks with `K[0xad] = 0x3ffff`; the split between the two words is not decoded: unknown.
- **Wrap or saturate.** Inferred: the GE7 side saturates. Colours and indices are clamped before conversion, and slopes whose magnitude would overflow take a separate path (GE7 3306 to 3310). What RE3's own iterators do when a step overflows is not visible from the microcode: unknown. It would take an RE3 register capture with a deliberately overflowing slope.
- **Flat-colour interval.** The console span routine (PNT2I, GeFifoTest) writes a constant colour and no slope, so the interval at which a flat span steps its colour cannot show. The console routines write `2` (points and spans) and `0` (rectangles) to RE3 `0x5f`, and the GL triangle, quad and polygon code writes the constant `1` at 25 sites (GE7 4226 to 10886); command `3` is not written as a constant at any site (87 sites compute the word and were not resolved). Which numbers name which RE3 operation, and any 5 or 20 interval, are not in the shipped microcode: unknown. The final iterator value after a span is not in it either.

## Mode-word fields

State tokens do not write RE3 from scratch: each routine reads a stored copy of one RE3 mode word, changes a bit field and writes the word back to RE3 and to its copy. Probing each routine with one operand at a time on a zero copy gives the fields below (`ge7-step.py run IMG START --slot N=V --unknown-lines low`, nine cases in `selftest`). Token names are the GL functions that send each slot ([pipeline.md](pipeline.md#what-the-gl-core-pushes)); operand counts match the HQ2 slot code ([hq2-slot-table.md](hq2-slot-table.md)). Bit fields are inferred from the routines. The host encodings are inferred (source build not located), so each host note below carries that grade.

| RE3 word | Token (slot, GE7) | Field | Notes |
|---|---|---|---|
| `0x62` | SetPixWritemask (3, 1607) | whole operand | the pixel write mask |
| `0x63` | PassLogicOp (26, 1655) | bits 3:0 | the GL core sends the low four bits of the GL logic-op enum (CLEAR 0 to SET 15), and 3 (COPY) when logic ops are off. Host side: inferred (source build not located). |
| `0x63` | PassBlendFunc (37, 2720) | bits 6:4, bits 9:7 | source and destination factor codes, 3 bits each |
| `0x63` | PassBlendFunc (38, 2736) | bit 21 | blend enable; the core sends blend state to the hardware only when the blend equation is the plain add (it takes a software path for MIN, MAX, subtract and reverse subtract, enums `0x8007`, `0x8008`, `0x800a`, `0x800b`); inferred from the first comparisons of `__glExpPassBlendFunc`, the factor encodings were not read. Host side: inferred (source build not located). |
| `0x63` | EnableDither (17, 1662) | bit 19 | the core writes 0 before and 1 after each clear. Host side: inferred (source build not located). |
| `0x63` | PassShadeModel (19, 1587) | bit 15 | set for GL_FLAT (host sends 0), clear for GL_SMOOTH (host sends 1). Host side: inferred (source build not located). |
| `0x65` | PassDepthFunc (36, 1736) | bits 2:0 | GL compare enum minus `0x200` (NEVER 0 to ALWAYS 7): the core sends `enum & 7`. Host side: inferred (source build not located). |
| `0x65` | EnableDepthTest (20, 1713) | bits 11:10 | the core sends 1 when the test and a Z buffer are on. Host side: inferred (source build not located). |
| `0x61` | PassStencilMask (16, 2169) | bits 3:0 | operand ANDed with `(1 << n) - 1`, n the plane count kept in bits 22:20 of the stencil word |
| `0x61` | PassDepthMask (10, 1752) | not isolated | the same word; the field depends on kept state |
| `0x66` | stencil mode (15, 2137), 7 operands | bit 23 enable; bits 3:0 and 10:7 two 4-bit operands; bits 6:4 compare function; bits 13:11, 16:14, 19:17 fail, depth-fail and pass ops | function 0 to 7 as for depth; op codes KEEP 0, INVERT 1, ZERO 2, REPLACE 3, INCR 4, DECR 5 (`__glExpPassStencilMode`); bits 22:20 are carried over from the stored word. Host side: inferred (source build not located). |

Consequences for a model:

- **Blend is hardware, with mode bits.** The TR's pixel-operations block "reads the destination pixel value at the address of the incoming pixel" for blending or raster operations [public], and the GE7 routines above load its factor and enable bits. A model that blends in the geometry path is not the board's structure; the arithmetic (rounding, the 8-bit multiply) is still unknown. The TR recommends blending into a 24-bit, single-buffered RGB framebuffer (established [public]). That this fits the blend fields, a blend of the stored 4-4-4 values in double-buffered mode, is inferred: the TR does not say so.
- **Order.** The TR places blend or logic op, fog and dither in the pixel-operations block ahead of the update tests; screen masks, clipping ID, Z and stencil are evaluated together and all must pass [public]. So the read-modify-write result is computed before the write is gated.
- **Dither is the pack.** "Incoming 24-bit pixel values are dithered into 4-bit red, 4-bit green, 4-bit blue" [public]: there is no separate pack stage to place the dither before or after. The 253 constants in the GE7 image contain no matrix, so the matrix and its anchor are internal to RE3: unknown, and only a pixel read-back from a board in a dithered mode can give them.
- **Stencil.** The TR lists clear, write, increment and decrement [public]; the microcode and the GL core also carry an invert code, and which of RE3 or the GE7 runs it is unknown. Inferred: the stencil planes are the low bits of Z, and the mask is limited to the plane count.

## Set-up and the hand-off

- **Who walks edges.** The TR gives the walk to RE3's DDAs, which iterate "in full-pixel steps" from start values and slopes loaded by the geometry subsystem; the GE7 computes the bottom pixel centre of a triangle, the edge slopes and the parameter slopes in floating point and corrects every colour and depth component to the first pixel centre [public]. The microcode agrees: the polygon set-up is one parameter set followed by one command, not a loop of spans (GE7 3157 to 3305). Inferred for the command, since the routine's own command word (GE7 3304) is computed.
- **Order of writes in the polygon set-up routine (GE7 3157 to 3305, started by BeginPolygon and EndPolygon; established [binary] for the order).** `0x25 0x24 0x23 0x20 0x21` (edges), `0x00 0x08 0x22 0x10`, then four colour groups `0x52 0x46 0x4c 0x40`, `0x53 0x47 0x4d 0x41`, `0x54 0x48 0x4e 0x42`, `0x55 0x49 0x4f 0x43`, then `0x57 0x56 0x45 0x44 0x4b 0x4a 0x51 0x5f 0x50`. The registers fall in four banks of six, `0x40` to `0x45`, `0x46` to `0x4b`, `0x4c` to `0x51`, `0x52` to `0x57`: the first four of each hold the red, green, blue and alpha quantity of that bank, and the last two (`0x44 0x45`, `0x4a 0x4b`, `0x50 0x51`, `0x56 0x57`) a two-word quantity that is the output of the exponent-normalising conversion above. Bank `0x40` to `0x45` alone is what points, spans and clears use (`0x40` to `0x42` for colour). Inferred: the banks are a start value and three slopes, and the two-word quantity is Z; which bank is the X slope, the Y slope or the edge slope is unknown.
- **Command word.** `0x5f` is written last: 1 at 25 triangle, quad and polygon sites, 2 for points and spans, 0 for rectangles, `0x200000` and `0x200002` for pixel transfers and a few other routines, a computed word at GE7 3304. Inferred from the writes; the mapping from a number to an RE3 operation is unknown.
- **Slope formats.** The conversions multiply by 4096 and then convert with FIXA; some paths mask with `0x3ffff` and shift by 4, 9 or 11; start values are split with the mask `0xfffff800`, which on a float also truncates the mantissa to its top 12 bits (71 words use it, on both integers and floats), so its role is ambiguous. The bit-level slope and edge formats are **unknown**. The route is a run of one triangle through GE7 3157 with the vertex data that the earlier stages (GE7 4610 on) leave in the RAMs, which needs the multiplier selects that no known answer fixes ([microcode.md](microcode.md#the-data-path)), and a capture of RE3 inputs for a triangle of known geometry.
- **Reset image.** Inferred: GE7 30, started by HQ2 slots 0 and 1, runs the same RE3 reset set as the console INIT when flag line `0x77` is high (for example `0x63 = 0x402413`, `0x66 = 0x100070`, `0x73 = 1279 << 11`, `0x74 = 1023 << 10`), and otherwise stalls without writing. The label "buffer swap" for GE7 30 in [devices/ge7](../../devices/ge7/README.md#what-the-shipped-microcode-does) rested on a token-table base address and is corrected there. A register read after initialisation is not a reset value.
- **A word after a cond 1 jump runs.** In 27 of the 56 words that follow a cond 1 word, the word carries real work (an RE3 write, a store or a non-trivial ALU operation) although nothing branches to it, and in the three colour groups above the write that completes the group sits right after a cond 1, 3 or 4 branch (GE7 3239, 3245, 3247, 3261). That fits a one-word delay slot after cond 1. It does not hold after cond 5, whose next word is a branch target in 181 of 189 cases and which FloatOps needs to be a plain jump. The existing model has no delay slot and passes every known answer, so the known answers do not separate the two: inferred for cond 1; unknown for conds 3, 4, 7 and 8, an open question in [questions/microcode.md](../../questions/microcode.md).
- **Store-address timing.** Inferred: the model's rule (a store uses the address a `0x31` word loaded, counting up per store) puts the mode-word write-back of the routines above at the wrong word when the load and the store share a word, and the long run of address loads at GE7 60 to 109 suggests a deeper pipeline or queue. How deep it goes is unknown, and no known answer separates the readings; nothing here depends on it except which store lands on a given state word, as noted under the colour scale.

## Clipping, screen limits and engine division

- **Clipping.** TR: clipping against the six planes of the homogeneous view volume, additional user planes, a fast accept or reject test and Cohen-Sutherland when clipping is needed, then the perspective divide [public]. The microcode constants `K[0x54] = 2047`, `K[0x56] = -2047` and `K[0x55] = 2048` bound the viewport and scissor arithmetic (GE7 504 to 510, 549 to 552, 583 to 586): device coordinates are limited to plus or minus 2047, the range of the 12-bit biased coordinate. The screen constants are 1023, 1279, 1280 as floats. Clip-plane arithmetic and any guard band beyond the view volume: unknown; the clip code starts at the polygon and line end routines (GE7 4610, 14338) and was not traced.
- **Edge rules.** The epsilons `K[0x46] = 0.0005` and `K[0x3d] = 0.00508471` appear next to pixel-centre constants (`0.5`, read 111 times) in the set-up and rectangle routines; no routine was followed far enough to say they are ownership biases. Unknown.
- **Engines.** The TR gives one primitive per engine and four at a time, issued by the HQ2 sequencer; the host writes only the engine count (`NUMGE`) [binary]. The microcode shows per-engine result windows in shared RAM (a cond 14 word opens a window indexed by the engine, a cond 15 word closes it, which fixes the stride the host uses) and that all engines run one instruction stream. How primitives are dealt out, and how the engines' RE3 writes are serialised on the single output bus, is not in the microcode (a cond 11 word precedes the flush write and is read as an output-FIFO wait, unverified). Unknown; the HQ2 sequencer words (`0x80` control operands) would have to be decoded.

## Finish flags and the read port

The host sequence is established and lives in [host-contract.md](host-contract.md#finish-flags-and-the-finish--sync-mechanism): clear a finish flag, queue the command, poll the status bit; read results from shared RAM (`+0x12088`, `+0x1b000`) after the flag rises; the FIFO interrupt line follows a fill count against a threshold of 40, with a 63-word limit. New from the GE7 side: the image-read token (slot 344, GE7 27522) sends two RE3 writes (`0x5f = 1`, `0x4b = 1`) with a cond 11 word between them, which the existing notes read as a wait on the RE3 output FIFO (unverified), so a flag may be raised only after the RE3 pipe has taken the preceding commands. Inferred from the routine's shape, not from the HQ2 word that sets the flag, which is not decoded. For a model: a guest must wait for (a) FIFO room, (b) a finish flag after any command whose result it reads, (c) the shared-RAM result; a GPU back end lengthens (b) and (c), not (a).

## Checks

`ge7-step.py selftest` passes, including two checks added with this page (mode-word fields, the Clear colour scale). The page leans on the model's open points listed under the sources; a value that depends on one says so.
