# Express (GR2) host contract on the Indigo

What a host program can observe and must provide at the graphics slot of an Indigo (IP20, with IP12 noted) so that the shipped PROMs, the IRIX kernel driver, the X server and the GL core run on a model of the board: status bits, flow control, completion flags, context switching, pixel DMA, probe answers per board variant, interrupts and reset. Written for the Indigo QEMU model and for the planned iris GR2 crate. The chip pages are [devices/hq2](../../devices/hq2/README.md) (command engine, register map in `registers.toml`), [devices/ge7](../../devices/ge7/README.md), [devices/re3](../../devices/re3/README.md), [devices/clock](../../devices/clock/README.md) (board configuration ports), [devices/vc1-express](../../devices/vc1-express/README.md), [devices/xmap5](../../devices/xmap5/README.md) and the DACs; the board survey is [README.md](README.md), the token catalogue [pipeline.md](pipeline.md) and the display back end [display.md](display.md). The host side of the buses is in the chips repository: `devices/mc` (graphics DMA engine, reset bit), `devices/int2` and `platforms/ip20/interrupts.md`, `platforms/ip20/gio.md` (slot window, probe).

Provenance tags on every fact: `[public]` published document or public driver (the Elan Graphics Technical Report, NetBSD `grtwo.c`, Usenet postings in the Library), `[binary]` a shipped binary (a software expectation; the routine or message is named), `[vendor-derived]` upstream headers (not used on this page). Grades as in [AGENTS.md](../../AGENTS.md): established (read in full), inferred (reasoned), unknown. Binaries read: the 5.3 `IP20boot/gr2.a` members for section 10 ([binaries.md](../../references/binaries.md#irix-53-install-disc-round-9)), `gr2.a` members (`gr2.o`, `gr2_dma.o`, `gr2_init.o`, `gr2_tpucode.o`), the IRIX kernel's graphics-DMA module (`vdma.o`, for the MC calls), PROMs 4.0.5D and 4.0.5G, the diagnostic program `ide.IP20`, the X server driver `gr2.so`, `libGLcore.so` (n32 and o32). Nothing was read on a board.

## 1. HQ2 status word, flow control and finish flags

### The status word (`status` at +0x6a040)

The diagnostic program prints this register, calls it the HQ2 version register, and decodes every field with a name (`gr2_rdHQ2reg`). Established [binary] for the field boundaries and names, which are the ones in `registers.toml`:

| Bits | Name (as printed) | Meaning and who uses it |
|---|---|---|
| 0 | finflag3 | Finish flag 3. Set by microcode, cleared by a store to `finish3`. Used by the kernel (`Gr2SetMonitor`, `Gr2PcxSwap`, `Gr2DestroyDDRN`) and the X server image paths. |
| 1 | finflag2 | Finish flag 2. Cleared by a store of 0 to `fin2`. The kernel's microcode-ready and DMA-done flag (`_Gr2UcodeReady`, both DMA triggers). |
| 2 | finflag1 | Finish flag 1. Cleared by a store of 0 to `fin1`. The diagnostic program's DMA-done flag and the 4.0.5G PROM's pixel-DMA completion flag. |
| 4:3 | dma_sync source | Read-back of `dmasync`: 0 vertical interrupt, 1 video sync, 2 clear, 3 set. |
| 5 | FIFO overflow | The kernel handler prints "FIFO overflowed, data is destroyed - Reset graphics" when set and then calls `gr2_error` (logs the GE PC from `hq_gepc`, flags the board, kills the graphics clients, resets the board). Nothing clears it in shipped software; inferred cleared by the graphics reset. |
| 12:6 | FIFO count | Words in the FIFO. The kernel compares it with 35 (room), 36, 40, 41 and 63. |
| 13 | FIFO low water | Never read by IRIX. Condition unknown. |
| 15:14 | zero | Printed as zero. |
| 19:16 | ge_ctr | Role unknown. |
| 22:20 | ge_ptr | Role unknown. |
| 31:23 | HQ2 version | Both PROMs store `word >> 23` through a byte store (bits 30:23). NetBSD masks `0xff000000` and shifts 23, a different field; they agree only at 0. |

The status bits 1 and 0 decoded: bit 1 is finish flag 2, bit 0 is finish flag 3. The kernel review note "bits 1 and 0 also tested" refers to these. Established [binary] (messages "finish flag not clear" in `Gr2SetMonitor`, the ide field names, and the three clear registers).

### What raises the FIFO interrupt and how it clears

- The interrupt is GIO line 0 (INT2 local interrupt 0, bit 0, `LIO_FIFO`). The kernel registers `Gr2FIFOInterrupt` on it for the graphics slot (`gr2_init`). Established [binary]; line routing in the chips interrupts page.
- The line is a level that follows the FIFO fill count against `fifo_full`. Every PROM drawing routine waits until bit 0 of the INT2 local-0 status byte is clear before each token, then sends a bounded run of operands (at most 25 words for a character strip) without checking again; `fifo_full` is 40. Established [binary] for the polling; **inferred** for the rule "asserted while count >= `fifo_full`", from the PROM budget (40 + 25 fits a 64-word FIFO) and from the kernel handler, which after an interrupt raises `fifo_full` to `min(count + 1, 63)` but not below 40 and masks the INT2 bit, the way one silences a level interrupt. The handler's own test (`sltu count, saved_threshold`, IRIX 5.3 `gr2.o` `0x1000035c`) treats count below the threshold as drained, a software expectation of `>=`; the hardware compare is **unknown** (`>` or `>=`), and no shipped read settles it: the kernel writes `fifo_full` 40 and, after an interrupt, `count + 1`, which is correct under either rule, and the IRIX source tree states only the threshold's name and the values 40 (kernel and PROM library) and 48 (the diagnostic program's `inithq`), never the compare. The Everest graphics path in the same tree tests a different board's word count against 50, which is not evidence for this one. Model: `>=`, inferred; a qtest can write `fifo_full = N`, push words with nothing consuming them, and check whether the line asserts at count N or N + 1.

Does anything else raise the line? Nothing shipped depends on it. The handler reads the overflow bit (status bit 5) on every entry, so overflow reaches the same handler, but overflow means a count past the threshold anyway, so no second source is needed to explain it. `fifo_empty` (written 1 by the kernel, 16 by the diagnostic) is called unused in a comment in the IRIX source library, and status bit 13 (low water) is never read, so no low-water condition drives a line that software relies on. The two timeouts (`fifo_full_timeout` 100, `fifo_empty_timeout` 255 in the kernel, 10 in the PROM library) are written and never read back; whether the hardware raises the line on a timeout is **unknown**, and the kernel's own "FIFO TIMEOUT" messages come from a software timer (`Gr2FIFOTimeoutCallback`), not from a status bit. Established [binary][source] for each of these absences of use.
- Kernel use: `Gr2FIFOPollLowater` returns 1 (room) and writes 40 to `fifo_full` when the count is below 35, and returns 0 without a write otherwise; a caller (not read) sleeps until it says yes, or a timeout callback fires. The handler masks INT2 local-0 bit 0 on entry (byte at `0xbfb801c7`), checks `fifo_overflow`, then compares count with the saved threshold. At or above it, it spins up to a software limit while count >= 36; below it, it either returns or, when that software limit is zero, spins while count >= 41 (limit 300000 us). When a context flag allows, it raises the threshold to `max(40, min(count + 1, 63))`, sets a "FIFO full seen" flag and forces a reschedule so the producer yields. It sets the mask bit again on exit. Established [binary] for the individual compares and stores; the branch conditions that select each path were read only in outline.
- The handler never writes a clear register: the line drops when the count falls below the threshold or the threshold is raised. Inferred.
- `intr` (+0x6a074, "Intr bit (cleared by host)" in ide) is a separate host-cleared bit; no driver touches it. Which line it drives is unknown.
- The fill count is in words: every store to the FIFO window adds one, and the microcode consumes them. A model that executes no microcode must drain the count itself (consume tokens as it interprets them) or the line would stay asserted.

### FIFO depth, thresholds and low water

- **Depth: 63 words, as the shipped developer header states. Software expectation.** The header `sys/gr2hw.h` that both the IRIX 5.3 and 6.2 discs install defines the maximum FIFO depth as 63 with the comment "hardware limit", the high-water depth as 40 and the low-water depth as 35, next to the finish-flag masks 4, 2 and 1 (status bits 2, 1 and 0) [binary] ([binaries.md](../../references/binaries.md#irix-62-install-disc-round-10) has the hashes; identical values in both releases). They agree with the kernel (`fifo_full` 40, the poll's 35, the clamp of its raised threshold to 63). The count field (status bits 12:6) is seven bits wide, so the field could hold more; the 63 is the header's limit, not the field's. The upstream header's "512-word FIFO" [vendor-derived] contradicts both its own note that the field holds 0 to 127 and this header; it is not used. The diagnostic program's FIFO RAM test (microcode stalled after a graphics reset, four dummy words queued) walks the window in blocks of 64 words, writing a block and reading it back ([source]: `stand/arcs/ide/fforward/graphics/EXPRESS/RAMtools.c`, `FIFO_LIMIT`); that is a window-walking stride, not a stated depth. The 32768 in the same table is the window size in words.
- **Full: the interrupt line asserts at a count of `fifo_full` or more. Inferred, not settled.** The threshold is 40 in the kernel and the IRIX PROM library, 48 in the diagnostic program, and the kernel raises it to `min(count + 1, 63)` (never below 40) after an interrupt and writes 40 back when it finds the count below 35. The PROM sends at most 25 words after the INT2 FIFO bit reads clear: with a 63-word limit that overshoots by one at a count of 39 and by two at 40 if nothing drained, so the budget does not separate `>=` from `>`; the board drains while the words arrive. Model `>=`, graded inferred. No shipped software tells the two rules apart: the kernel's raise to `count + 1` and its `count < threshold` drained test are the authors' expectation of `>=`, and both rules satisfy them (under `>` the raise could have been `count`, and one extra word of headroom does no harm). Nothing in the IRIX source writes exactly `fifo_full` words and tests the line (the diagnostic's HQ2 menu only writes the register; the other FIFO flow-control text in the tree, for the IP26 processor board, is another machine). A qtest pins only the model's choice; it cannot show which rule the hardware has.
- **Overflow (status bit 5): a word arrives with 63 queued. Inferred.** The kernel treats it as fatal ("FIFO overflowed", `gr2_error`) and nothing clears it but a graphics reset.
- **Low water (status bit 13) and `fifo_empty`: unknown.** Bit 13 is never read by IRIX. The register is written 1 by the kernel and the IRIX PROM library (a comment there says it is not used), and 16 by the diagnostic program. The header's low-water depth of 35 is the kernel's own "room again" level in `Gr2FIFOPollLowater`, a software constant, not the `fifo_empty` register. The upstream header reads bit 13 as "count at or below `fifo_empty`" [vendor-derived, inferred at best]; with the kernel's value of 1 that would mean "at most one word queued", which no software checks. A model may drive the bit that way; nothing depends on it. The two timeouts are in [the interrupt section above](#what-raises-the-fifo-interrupt-and-how-it-clears).

- **Count field position: status bits 12:6. Established [binary].** The diagnostic program masks and shifts exactly that field, and the kernel's compares (35, 36, 40, 41, 63) use it; the unit is words queued ([section 1](#the-status-word-status-at-0x6a040)).
- **Drain rate: unknown.** No source gives HQ2 cycles per FIFO word or the rate at which the geometry engines take work. The nearest published figures are the Elan technical report's: the HQ2 has "several clock rates with speeds up to 33 MHz", each GE7 is rated 32 MFLOPS (128 for four), the RE3 runs at 50 MHz [public]. The shipped timeouts are software budgets, not rates (a 100,000 x 1 us wait for a finish flag, a 300,000 us wait in `Gr2SetMonitor`, the diagnostic's fixed `time_delay` calls of 1000 to 1500), and the HQ2 slot code is a few words to a few dozen per command while the GE7 routine behind it runs for hundreds to thousands of words, so the GE7 side paces the drain. A modelled drain rate is an approximation, to be rated as such.

### The FIFO rules a driver has to obey

Three questions a driver asks, answered from what the shipped software does, the GR4 board schematic and the GIO specification (all [public] or [binary]; nothing was run).

- **A store to a full FIFO: stall or overflow? Unknown for the Indigo; both outcomes are possible in hardware.** The chip has an overflow flag (status bit 5), which the kernel treats as loss of data ("FIFO overflowed, data is destroyed", section 1), so a word can arrive with 63 queued and be dropped.
  The bus protocol also lets a slave hold a write off: a GIO32 slave stretches a cycle with SLVDLY, and a GIO32 transaction a slave holds for more than 25 microseconds ends in a bus error from the arbiter (GIO specification, section 2.7, Library `graphics/indy/erikarn-sgi_indy_gio64.pdf`);
  a pipelined GIO64 slave drives its own GRXDLY line, "asserted when the device cannot accept data in two clocks" (GIO64 chapter, signal list). The GR4 board schematic wires the HQ2's `GRXDLY` pin (sheet 7, pin 216) through a register to the GIO connector as `PG_GFX_GFXDLY`
  (sheets 3 and 2), and its `FIFO.FULL` pin (pin 209) to the connector as `GFX_FIFOFULL_N`, which is the line software sees as INT2 local-0 bit 0 (inferred from the signal name and section 1's polling). So that board's HQ2 has a write back-pressure output and a separate full output; the comparator that
  drives each is inside the HQ2 and not drawn. Two timeout registers (`fifo_full_timeout` 100, `fifo_empty_timeout` 255) are written by the kernel and never read; a reading that fits everything is "the HQ2 holds the bus while the FIFO is full, for at most the full timeout, then lets the write overflow". That is inferred from the register
  names, the pins and the overflow flag together and no source states it. **What a driver should do is what the shipped software does: never rely on either outcome.** Wait for INT2 local-0 bit 0 to read clear before each token, and send no more words after it than the room above `fifo_full` allows
  (the PROM sends at most 25 after a clear reading). A model should stall the writing CPU (or the host store) while the count is at the depth limit and set the overflow flag only if it is asked to model the loss. Settled by: the HQ2's internal logic (not held), the Indigo's own graphics board set (not held), or a hardware test (not permitted by the workspace rules).
- **The `fifo_full` compare: `>=` or `>`.** Still unknown; section 1 has the evidence and the model choice. The schematic does not help, because the count and the comparator are inside the HQ2 (sheet 7 shows `FIFO.FULL` as an output pin only).
- **Is a store to a slot with no HQ2 word harmless?** Not decided by any shipped code, but shipped software does it constantly, so a model must accept it. Slot 490 (`+0x407a8`), which the X server stores to at the end of every list it sends ([x-server-tokens.md](x-server-tokens.md)), has no first-level word in the 6.5 `hq2.bin`; slot 99 (vertex) has none either and is resolved through the attribute table by address bits 15:12.
  Slot 490's address has bits 15:12 equal to 0, which selects attribute table entry 0 (microstore address `0x304`, which holds a short routine of attribute loads and `op81 0000` words), but that the HQ2 dispatches an empty slot through the attribute table is inferred from slot 99 and not shown for 490. Slots 403 and 409 (console `FINISH` and `RECTCOPY`) are the unloaded case no shipped program sends to the full image. Model: consume the store as a one-word command with no
  effect and log it. Settled by: decoding the HQ2 dispatch, which needs its instruction set ([microcode.md](microcode.md)).

### Finish flag 2 (status bit 1): when it rises, and what clears it

- **A store to `fin2` of 0 drops it. Established [binary] as software expectation.** Every user clears the flag first and then queues a command that must raise it: `Gr2Start` (the class word, below), the context save and restore (`_Gr2CXSaveRestore`, `Gr2PcxSwap`), both DMA triggers, and the diagnostic program's `diag_finish`, which then writes slot 1 and tests bit 1. The IRIX source says the same of the diagnostic: `diag_finish` in `ge7diag.c` clears `fin2`, stores 0 to slot 1 (`DIAG_FINISH2`, "sets finish flag 2" in `diagcmds.h`), waits a caller-chosen delay, fails with "GE7 not responding" if status bit 1 is still clear, and clears `fin2` again [source]. So bit 1 is a level that stays set until the host clears it, and it rises only after the microcode has run the command. A flag that survived the store would let each wait pass at once. The write port sets the flag to the stored bit 0, so a store of 1 would raise it (the diagnostic's menu offers it; no driver does it).
- **Raised only once the full image runs? Not decided by any shipped code.** The kernel waits on bit 1 only after the full HQ2 and GE7 images are loaded and started: its start-up wait is `Gr2Start`'s, after it has cleared `fin2` and sent the board class word. The console images (the PROM's and the kernel's built-in pair) are driven without any bit 1 wait, and the HQ2 instruction that sets a finish flag is not decoded, so whether a console routine can set one is not known. The model that fits all shipped waits: raise bit 1 when the microcode has retired the command that was queued after the last store to `fin2`, and for the start-up wait when the class word has been consumed with the full image loaded. Raising it earlier (for instance at download time) cannot be seen, because `Gr2Start` clears the flag immediately before the class word; whether the hardware can raise it with the console images is unknown.

### Finish flags and the FINISH / sync mechanism

Three flags, each set by microcode when it runs a finish-type command, each with a host store port that sets the flag to the stored bit 0 [binary]:

| Flag | Status bit | Host store | Users |
|---|---|---|---|
| 1 | 2 | `fin1` (+0x6a048) | `ide` DMA tests; 4.0.5G PROM pixel DMA |
| 2 | 1 | `fin2` (+0x6a04c) | kernel context swap, microcode start, DMA |
| 3 | 0 | `finish3` (+0x6b000) | kernel monitor change, context swap restore, X server image read and write, GL finish and read-back sequences (through the user mapping, see question 2 of [questions/hq2.md](../../questions/hq2.md)) |

The host sequence is the same for each: store 0 to the flag port, queue the command, poll the status bit. Examples, established [binary]: the X server `expReadImage` stores 0 to `finish3`, queues token slot 344 and its four operands, then polls status bit 0 and reads pixels from shared RAM at `+0x1b000`; `Gr2SetMonitor` queues slot 2 with operands 0x6c and (screen height - 1), polls bit 0 with 10 us sleeps (limit 300000), then stores 0 to `finish3`. The GL origin query (`__glExpGetOrigin`; slot 163 is shared with Finish and SwapBuffers) stores operand 0 to slot 205 (`+0x42334`) and slot 163 (`+0x4228c`), then polls bit 0 at `+0x6c040`, reads two results from shared RAM and stores 0 at `+0x6d000` in the user mapping; those two offsets are not the kernel's (see the question).

The FINISH token NetBSD names (`+0x4064c`, slot 403) is not used by any shipped program and has no word in `hq2.bin`. Which microcode routine sets which flag is not decoded (HQ2 instruction set unknown), so a model must set a flag when it has retired every earlier command (inferred: that is what the shipped callers wait for).

Reset values software relies on: none. Software stores 0 before every use; `probe_word` reads 0xdeadbeef before any initialisation.

### The HQ2 revision: PROM or kernel?

Answer: both read a register, they read different ones, and a model that returns 0 from both is right for every Indigo board on record.

- **What gfxinfo prints.** `gfxinfo` is `usr/gfx/gfxinit` (5.3 disc; the name is a symlink to it). Its GR2 report formats the 60-byte probe record the kernel copies out through `Gr2Info`. Record byte `0x30` selects the HQ2 text: 0 prints "HQ2 rev A", 1 prints "HQ2.1 rev A", anything else "HQ2 rev unknown" (`gfxinit` `0x40aa04` to `0x40aa60`, strings at offsets `0x2844` to `0x2860` of the data segment, file offsets `0x24844` to `0x24860`). Established [binary]. Public captures agree: every Indigo board (GR2 revision 2) prints "HQ2 rev A", and the later GR2 revision 4 and 6 boards (Indy and Indigo2) print "HQ2.1 rev A" (Library mail archive, `3EBA4AA5.8080302@sgi.com`, `20071209164502.GA13877@deprecation.cyrius.com`).
- **Where the kernel gets byte `0x30`.** From bits 23:16 of the word at `+0x6a06c` (`hq_gepc`): `_Gr2ProbeChipRev`, IRIX 5.3 `gr2_init.o` `0x100001dc` to `0x100001e4` (a word load, a shift right by 16, a byte store), the same in 6.5. Established [binary]. The same register's low 16 bits are the GE program counter that `gr2_error` logs.
- **Where the PROMs get theirs.** From bits 31:23 of the status word at `+0x6a040` (`word >> 23` through a byte store; 4.0.5D `0xbfc0ecec`, 4.0.5G `0xbfc11a98`). The IRIX source's PROM library does the same (`info->HQ2Rev = base->hq.version >> 23`, `stand/arcs/lib/libsk/graphics/EXPRESS/gr2_init.c`) and the diagnostic program prints the same field as "HQ2 version". Established [binary][source]. Nothing in the PROM path reaches gfxinfo; the kernel reprobes.
- **Which one is "the revision".** Not settled by software: the two fields would agree only at 0, and 0 is the value for every captured Indigo. The kernel's field is the one users see (value 1 = HQ2.1). For a board that reads 0 in both, the Indigo, nothing depends on it. Model: `status` bits 31:23 = 0 and `hq_gepc` bits 23:16 = 0 for HQ2 rev A, which is every Indigo configuration. If an HQ2.1 board were ever modelled, put 1 in `hq_gepc` bits 23:16 (what gfxinfo needs) and 1 in status bit 23, the PROM-side placement being a guess. NetBSD masks `0xff000000` and shifts 23, a different field again [public]. Grade: the decode and the captures established; "register A is the revision and register B is not" unknown.

### The other revision read-backs gfxinfo prints

The same record carries three more chip revisions. The decode tables are in `gfxinit` (the three letter tables at data-segment offsets `0x2870` to `0x28dc`, file offsets `0x24870` to `0x248dc`), established [binary]; the values the captures need are inferred from them.

| Record byte | Source in the kernel | gfxinfo decode | Capture (XS24, XZ, Elan) | Value to read |
|---|---|---|---|---|
| `0x31` GE7 | word at `+0x683f4` after a store of 0, byte bits 7:5 (`gr2_init.o` `0x100001e8` to `0x100001f8`) | 1 = A, 2 = B, else unknown | "GE7 rev B" on all | `0x40` in the low byte (field value 2) |
| `0x32` RE3 | low byte of shared-RAM word `+0x1ffe0`, copied in `Gr2Start` and on the reuse path; the microcode writes it (`Gr2Start`'s failure message is "RE version read back failed") | low nibble 1 to 4 = A to D (RE3), 5 = A (RE3.1), else unknown | XS24 and the IP12 Elan 4D/30 posting: D and C; XZ postings: "unknown" | 4 for rev D; the INIT routine must leave it |
| `0x33` VC1 | `testreg` low three bits after `addr = 5` (`Gr2ProbeVC1`) | 1 = A, 2 = B, else unknown | "VC1 rev B" on all | 2 |

An earlier version of this page and of the GE7 and VC1 register maps said the value for rev B was 1; the decode above shows A is 1 and B is 2.

## 2. Context save and swap (`_Gr2CXSaveRestore`, `Gr2PcxSwap`)

The kernel never copies board state itself. It asks the microcode to dump or load it, and moves the data with the MC graphics DMA engine (section 3). Established [binary] for the calls below (`gr2.o` `0xbe0`, `0xe00`); the structure of the per-context records is inferred where noted.

`_Gr2CXSaveRestore(board, buffer, bytes, token_slot, token_operand, direction)`:

1. Store 2 to `dmasync` and 0 to `fin2`.
2. Queue a token at slot `token_slot` (481, 482, 483 or 484, i.e. `+0x40784`, `+0x40788`, `+0x4078c`, `+0x40790`): 481 stores 0 (the caller's operand is ignored), 482 stores the word count (`bytes / 4`) as its first operand, 483 stores `token_operand`, and 484 stores `token_operand` and then sends the word count to the data port (`+0x4077c`). Established [binary] (`gr2.o 0xc3c` to `0xdbc`).
3. Run a DMA of `bytes` between the buffer and the DMA port `gedma` (section 3), direction 2 = board to memory (the save path passes 2), 0 = memory to board (zero means write back, nonzero means invalidate); cache write-back before a load, invalidate before a save.
4. Poll status bit 1 (`_Gr2UcodeReady`, up to 1,000,000 us). On failure print "_Gr2CXSaveRestore: TIMEOUT gfx data could not be saved/restored".

Token meaning (inferred from the callers; the operand details are in [the next subsection](#what-the-context-operands-are)): 481 and 482 move the context's whole shared-RAM image ("get initial state" and "load state"); 483 saves and 484 restores one of four state buffers selected by the operand 0 to 3.

`Gr2PcxSwap(board, old, new)` sequence (inferred as a whole; the individual stores are established):

1. Take the graphics context lock (`gfx_waitc_on`). Reject a context whose type is not below 4 or size class not below 3 ("Invalid gfx context type/size").
2. Save the outgoing context's finish flag: read status bit 0 into its record.
3. Save each of the outgoing context's valid state buffers (flags in the record word at +0x48, bits 0 to 3) with token 483 and operands 0 to 3; allocate buffers on first use.
4. Restore the incoming context: store 0 to `fin2`; queue slot 496 (`+0x407c0`) with the render-node index (record address minus the node array base) and send the context type and size to the data port; wait for status bit 1; then for each valid buffer token 484 with its operand; send per-window setup (slot 485 `+0x40794` window box, slot 486 `+0x40798` flag, slot 480 `+0x40780` flag, and clip rectangles as packed 11-bit pairs through the data port) when the window changes.
5. Store the incoming context's saved finish flag bit to `finish3`.
6. Errors: "Gr2PcxSwap: TIMEOUT gfx" with a reason ("context switch did not complete (Start)", "(Restore)", "(Kill)", "(CX current RN)", "Context Size change did not complete").

What the hardware must preserve: the diagnostic program's context-switch test (`gr2_ctxsw`, message "CTX_SWITCH DMA test") shows the state that a save and restore must round-trip, by printing each field of context 0 before and after: `Attr_store[n]`, `Cmds_store[n]`, `Cmdreg`, `Vecreg`, `Datareg`, `Act_attr`, `Cur_attr`, `flag_reg`, `hq2pc_reg`, `cmdptr`, `vtxctr`, `fifostate`, `ucode_reg`, `finishflg`, and the first and second vertex coordinates `X_VTX`, `Y_VTX`, `Z_VTX`, `W_VTX`. Established [binary] that these are the compared fields; the register file they come from is inside the HQ2 microcode and sequencer, not host visible. The host-visible part is the finish flag (status bit 0, carried in the record) and the FIFO state (an incoming context starts with an empty FIFO count of its own, `fifostate`).

For a model that interprets tokens directly (no microcode): implement 481 to 484 and 496 as "DMA the model's per-context state to or from the host buffer"; the buffer contents are opaque to every shipped program, so any self-consistent format round-trips. Raise finish flag 2 after each. The shared-RAM words that give buffer sizes must be written by the model at start-up (otherwise the kernel allocates zero bytes). Inferred.

### What the context operands are

## 3. Pixel DMA (`gr2_dma.o`)

Answer: the MC runs the transfers; the HQ2 is a bus slave; the HQ2 does not start transfers itself.

- Engine and address. The kernel programs the MC graphics DMA engine (`MCdma`: memory address, mode, size, stride, then the GIO address, which starts it) with the GIO address equal to the physical address of the HQ2 `gedma` register (`+0x6a068` in the graphics window, `0x1f06a068` on the Indigo). Every transfer, pixel or context, uses that single address as the board port. Established [binary] (`Gr2MCPixDma` and `_Gr2CXSaveRestore` call `kvtophys(base + 0x6a068)`; `MCdma` stores the fields in the order in the MC page). Register and field meanings are in the chips repository's `devices/mc`.
- Mode. 0x54 for host to board (long burst, incrementing memory address, wait for the graphics sync) and 0x56 for board to host (the same plus the graphics-to-host bit). Established [binary] (`Gr2MCPixDma` stores 84 or 86). The sync bit ties the transfer to `dmasync`; the kernel stores 2 ("clear") before each transfer.
- Parameters. Line width in bytes is the word count per line times 4 (user argument at +0x24); the MC line count is the number of lines (in 16-bit halves); stride is the signed byte distance (the kernel negates for bottom-up and right-to-left reads, flags bits 2 and 3 of the argument half-word at +0x14); zoom 1. Transfers are limited to 8192 bytes per chunk when the MC has no virtual-address translation (MC revision 0, `vdma_rev` 0): the kernel then builds physical page descriptors (`_Gr2mkkdmada`) and walks them with a software DMA routine in 4096-byte pieces (`fakePICdma`). Established that both paths exist; the MC revision split is the MC page's.
- Formats. Argument flag bit 0 selects 84 or 86 (direction), bit 1 a strided/rectangle transfer, bit 2 and bit 3 the two reversal directions, bit 4 an extra mode used by the 32-bit packed read; the pixel formats (32-bit words, packed 16, 8 and 1-bit with colour expansion in the board) come from the GL tokens before the ioctl: `__glExpDrawPixelsKDMA` stores 1 to `+0x422f0` (slot 188), then `0` and two floats (x and y zoom) to `+0x422ec` (slot 187), then calls the kernel with slot number 184 or 181 and its operands. Established [binary] for the sequence. The Elan TR says the DMA channel is 32 bits wide and carries 32-bit pixels and packed 16, 8 and 1-bit pixels, the latter expanded into one of two user-defined RGBA values [public] (section 5.11). Operand layouts of the board commands are the kernel arguments `[slot, first operand, ...]`: `_Gr2MCDMAtrigger` queues slot = argument 0, operand = argument 1, then data words from arguments 3, 2, a half-word of the MC argument block and argument 9, then a 1 or 0 for the direction flag. Argument semantics (origin, size) are not decoded: unknown.
- Handshake. Before: store 2 to `dmasync`, store 0 to `fin2`, queue the board command, then start the MC transfer. After: poll status bit 1 (`fin2`) at 1 us steps, up to 100,000 in `_Gr2DMAtrigger` and in one branch of `_Gr2MCDMAtrigger`; the other branch counts a software limit and, on each expiry, writes 0 to `gedma` twice and logs, up to ten times, then fails (the abort meaning is inferred). `_Gr2MCDMAtrigger` clears the MC done interrupt (`MCIntClr`) before it starts the transfer, but nothing in `gr2.a` waits on INT2 local 0 bit 4; that wait, if any, is inside the MC DMA routines (`vdma.o`, not read here). Established [binary] (`_Gr2MCDMAtrigger`, `_Gr2DMAtrigger`). The 4.0.5G PROM runs a pixel DMA the same way using `fin1` and status bit 2 with a 1000 us x 20 wait. The diagnostic program does the same with `fin1`.
- Can the HQ2 start transfers itself? **No: the host does, through the MC, and the HQ2 only answers as a GIO slave.** Established for all shipped software [binary][source]. The IRIX source's diagnostic DMA code (`stand/arcs/ide/fforward/graphics/EXPRESS/dmasetup.c`) is the clearest statement: `mk_dmada` writes the MC's memory address, mode (incrementing address, long burst, and a "sync" bit that the source says is always set for this board), size, stride and finally the GIO address (the HQ2's `gedma`), and `do_dma` then writes the MC's start-DMA register and waits for the MC to finish. For a board-to-host or host-to-board pixel transfer the host queues the board command first (token words to the FIFO, with `fin1` zeroed) and starts the MC afterwards, then polls `fin1` for up to 20 x 1 ms; the 4.0.5G PROM and the IRIX 5.3 kernel (`_Gr2MCDMAtrigger`, `_Gr2DMAtrigger`) do the same with `fin1` or `fin2`. No host-visible HQ2 register holds a memory address or length, and nothing in `gr2.a`, either PROM, `ide` or the GL core sets one. The diagnostic's comment "this sets up HQ2 with DMA" refers to the board command that arms the board side, not to bus mastering. What stays **unknown** is whether the silicon could master the bus: the HQ2's internal registers and microcode are unread, and no shipped program asks. The model should never initiate a GIO cycle from the board.
- The sync bit. The MC's graphics-DMA mode carries a "graphics sync" bit that the kernel and the diagnostic always set (mode `0x54` and `0x56` above). It pairs with `dmasync` (+0x6a050): the kernel stores 2 ("clear") before each transfer and the diagnostic menu names 0 vertical interrupt, 1 video sync, 2 clear and 3 set. How the MC gates its cycles on the board's sync is the MC page's; what software relies on is only that, after it stores 2 and queues the board command, the transfer runs to completion and the finish flag rises. A model should not stall the MC on the sync; whether "clear" means gated off or released is **unknown**.
- What a model must do. Treat the MC DMA engine as already implemented in the MC model; give it a GIO slave at the `gedma` address that accepts and returns words for the length, and set finish flag 2 (or 1) once the board command has consumed the last word. The words are the board's pixel stream: framebuffer or Z, 32 bits each, in the order the board command selects.

### Operand layouts, packing and the read-back

- **The board command.** `_Gr2MCDMAtrigger` (`gr2_dma.o` `0xad4`) queues `[S slot <- x]` and then, on slot 0 as the data port, **the first y, the width, the line count of this transfer, the words per line and one flag word (1 when bit 3 of the argument flags is set, else 0)**; before it `dmasync` is set to 2 and `fin2` to 0, and after it the MC engine is started with a descriptor of memory address, line bytes, line count, stride, zoom 1, the `gedma` address and mode `0x54` or `0x56` (`Gr2MCPixDma` `0xd0c`). The word-by-word layout of the 0x2c-byte argument record, the sender fields in the X driver and the thresholds
  between the FIFO and DMA paths are in [x-server-tokens.md](x-server-tokens.md#image-write). Established for the stores and fields; the names are inferred. The GL core's sender (`__glExpDrawPixelsKDMA`) uses slot numbers 184 (flags `0x11`) and 181 (a second path whose flags may add bits 2 and 3); what 181 and 184 differ in on the board is not decoded.
- **Packing.** From the X driver ([x-server-tokens.md](x-server-tokens.md#rectangle-copy)): 8-bit pixels go four to a 32-bit word with the source's low two address bits sent as an alignment word; 24-bit pixels go one to a word; the packing code in slot 337 is 2 for 8-bit (and for the 2- and 4-bit plane windows), 1 for 12-bit and 0 for 24-bit, and words per row follows
  `(width + alignment + 3) >> 2`, `(width + 1) >> 1` and `width`. Established for the codes and formulas read in the copy and 8-bit and 24-bit image functions; the 12-bit packing (two to a word) is inferred from the formula. For GL: format `0x1908` selects the byte-swapped copy loop (`__glExpSwapToPipe4`, [icd-sequences.md](icd-sequences.md#51-gldrawpixels-by-fifo-words)); other layouts were not decoded.
- **Slots 177 to 179, 186 to 189 for GL.** As sent ([icd-sequences.md](icd-sequences.md#5-one-image-transfer)): 177 strip start (one word), 178 row (x then y, width, width, direction), 179 row end, 187 three words (0, x zoom, y zoom or 1), 188 a 1 before a DMA write and a 0 before a read, 189 a 0 after a read, 186 `FastCopyPixels`. What the board does with each beyond that is not decoded.
- **The read-back.** An X read clears finish flag 3 (`+0x6b000`), sends slot 344 (`[S344 <- words per row]`, `D <- x, y, width, rows`), polls status bit 0, and reads the result from shared RAM at `+0x1b000`; the GL read of colour pixels reads from `+0x12088` after the same kind of poll (user-mapped aliases `+0x6c040` and `+0x6d000`). Up to 4096 bytes per group go this way in the X driver; larger reads use the DMA path. Each reader names its own area, so the area is chosen by the microcode routine, not by the host (inferred).
- **What the MC does.** The register meanings (memory address, size, stride and zoom, GIO address, mode, count, run and cause) are in the chips repository's `devices/mc/registers.toml`; the kernel writes them in the order the page above gives. **The descriptor's "little" bit:** no held source names one. The IRIX header `irix/kern/sys/mc.h` describes the pre-MR descriptor-array mode with a buffer address, a control word (full-page, last-entry and graphics-to-host flags), the GIO address, a word of stride and line count and a next pointer;
  it swaps the order of the two 16-bit halves under `_MIPSEL`, which leaves that word's value the same on both CPUs, and defines the register mode bits graphics-to-host, sync, fill, increment, snoop and long burst with no endian bit. So descriptor words are value-neutral (established [source] for the header), and what the engine does with pixel bytes for a little-endian host is unknown. The MC specification's revision history is the only place that mentions the bit. Settled by: the specification's DMA mode table or the Virtual DMA Programmer's Guide (neither held).

  is chosen by a jump table on the count (`0xbfc454f0`, code `0xbfc12604` onward): 8 "-8GE24Z" (the source says "-Extreme"); 4 "-Elan" with 24 planes, else "-XSM"; 2 "-XZ", with " missing bitplanes" and " missing Z" added when 24 planes or Z are
  absent; 1 "-XS24" with 24 planes, else "-XS", with "Z" appended when the Z flag is set; 3, 5, 6 and 7 " unknown GE configuration".

Which probe value selects which name, then: only the planes (`port3`), the Z flag (`port1`) and which GE slots answer matter; the monitor code and the other ports do not. Elan: `port3` `0x15`, slots 0 to 3 answer. XZ: `port3` `0x15`, slots 0 and 1 (4.0.5D prints Elan, 4.0.5G prints XZ). XS24 with Z: `port3` `0x15`, slot 0
only. XS: `port3` `0x3d`, slot 0 only. A model needs no change for 4.0.5D; for 4.0.5G the XZ must leave slots 2 and 3 unanswering, which the engine probe note below already requires. Not run here: 4.0.5G past its retrace wait, so its names are read, not observed.

Absent GE slots (question 6). The engine probe (`_Gr2ProbeGEs`, IRIX 5.3 `gr2_init.o` `0x10000054`; the PROM library and the diagnostic's `Gr2ProbeGEs` in the IRIX source do the same) stores five distinct words per slot for slots 1 to 7 and loads them back, with plain accesses, no `badaddr` guard and no exception handler, on every board it meets. Only the board probe (`Gr2Probe`) is guarded, and only at the probe word (`+0x6a07c`). The captured one-engine boards (XS, XS24: "1 GE") run IRIX this way for years, so an absent slot cannot raise a bus error on either the stores or the loads (inferred as a necessary consequence; the accesses themselves are established [binary][source]). What an absent slot reads is not fixed by any shipped code: a slot counts only if all five words come back, so any value that is not the pattern passes as absent. Model: absent slots accept the stores and read 0. Do not echo the stored words back: a model that remembers writes would make every slot present. The loop does not stop at the first miss; the count is the highest answering slot plus one, so the present slots must be contiguous from 0. Grade: inferred for the hardware, established for the software.

Unmapped offsets inside the window. **Unknown for the hardware; no software depends on it.** The shipped developer header `sys/gr2hw.h` (5.3 and 6.2; [binaries.md](../../references/binaries.md#irix-62-install-disc-round-10)) lays the window out as shared RAM (`+0x0` to `+0x1ffff`), 128 KiB of padding, the FIFO (`+0x40000`), the HQ2 microstore (`+0x60000`), eight GE7 slots (`+0x68000`), the HQ2 registers (`+0x6a000`) with padding up to the third finish flag at `+0x6b000` and more padding to the board version at `+0x6c000`, then the clock, VC1 and the other chip pages [binary]. No shipped program read here accesses the padding or anything above the highest register page it uses (`+0x6d000`): the diagnostic's RAM tests stay inside the named regions, and the kernel, PROM, GL core and X driver use the offsets of this page only. The one data point is the engine probe above: loads and stores to the absent GE slots, which lie inside the window, do not fault on the one-engine boards. Whether the board's address decode answers the other gaps or lets the GIO bus time out into a bus error is therefore not shown. The `badaddr` guard on the probe word exists for an empty slot, where the MC's own timeout fires, and says nothing about a present board. Model: accept stores and read 0 everywhere in the window outside the named regions, and log the access so a guest that depends on a fault shows up. Inferred for the model, unknown for the hardware.

Byte lane of a narrow probe read. Every narrow access the shipped code makes to the board ports is a byte at the first byte of the word, the most significant lane on this big-endian host: the kernel's `Gr2Probe` (`lbu` at `+0x6c000`, `+0x6c004`, `+0x6c008`, `+0x6c00c`), the PROM probe, the diagnostic program's `gr2_boardvers` (`lbu` at the same four offsets), `Gr2ProbeVC1` (`lbu` at `+0x6c04c`, `sb` at `+0x6c050` and `+0x6c054`) and the VC1 `sysctl` byte. Established [binary]. The GE revision is a word load of `+0x683f4` masked to its low byte, a different register. NetBSD reads the board ports as words and masks the low bits [public]; the two cannot both be right unless the gate array drives every lane alike. The model returns the value in the first byte and replicates it in the other three bytes of a word read, which satisfies both readers; a byte load must never come from any other lane. Which the hardware does is unknown, and no shipped program distinguishes them.

Byte position of the board revision: settled for every shipped program. The kernel (`Gr2Probe`), both PROMs and the diagnostic program (`gr2_boardvers`) all load a byte at the first byte of each word (the most significant byte position on this big-endian host). NetBSD masks the low bits of a word instead [public]. The model should return the value at the first byte of the word and, to satisfy NetBSD as well, replicate it in all four byte positions of a word read; whether the board does so is unknown. Established [binary] for the three programs.

## 5. Board outputs to INT2

Only two that any shipped software uses: GIO line 0 (FIFO, section 1) and GIO line 2 (vertical retrace; the `intr` register's line is unknown, so "only two" is inferred from the registrations; what enables the retrace line is in [vc1-express](../../devices/vc1-express/README.md#retrace-interrupt): the INT2 mask is set by `setgiovector`, and VC1 `sysctl` bit 0 set blocks the pulse). The retrace latch is cleared by pulsing bit 3 of the INT2 port byte `0xbfb801df` low and high (PROM at `0xbfc0ed60`), and the retrace status is also readable at bit 0 of the INT2 status byte at `0xbfb801d3` (the kernel handler polls it, up to ten times). `gr2_init` registers no handler on GIO line 1 (other drivers, such as the GIO Ethernet, use it). The MC graphics DMA done interrupt (INT2 local-0 bit 4) is the MC's, not the board's. Established [binary] for the registrations (`gr2_init` calls `setgiovector` twice) and the PROM stores; interrupt tables are in the chips repository.

The bit the FIFO handler touches, bit 0 of the byte at `0xbfb801c7` (and the status byte at `0xbfb801c3`), is the INT2 local-0 mask (status) bit for that same GIO line 0: it is not a second source. The handler clears the mask bit on entry so the level cannot retrigger while it runs and sets it again on exit. Established [binary] (`Gr2FIFOHandler`); the bit meaning is the chips interrupts page.

## 6. What the graphics reset clears

The reset is MC `cpuctrl0` bit 10 (active low): `Gr2Reset` clears it, waits 10 us, sets it; the PROM does the same with its own delay. Software never reads anything to see what the reset cleared; what it does afterwards shows what it assumes is lost. Everything below is re-initialised after the reset, in this order (`gr2_earlyinit`, `Gr2Init`, `_Gr2RegisterInit`, `_Gr2HQ2RegInit`), so a model that clears all of it satisfies the shipped drivers: the pixel clock (`Gr2StartClock`), the three Bt457 DACs, the XMAP5 chips (three init passes), the VC1 SRAM images and registers, the HQ2 registers (`numge`, the two timeouts, `fifo_full`, `fifo_empty`, `refresh`), the HQ2 and GE7 microstores and the shared-RAM constants (downloaded again; the PROM loads its built-in console images, the kernel the built-in image then the full images through an ioctl), the unstall and GE program counter writes, the INT2 retrace latch, and the FIFO count and flags. After the reset the kernel does not write status flags or `intr`, so it assumes they are cleared. Established [binary] for what is re-written; "reset clears it" is **inferred** for each item, because no program checks. What survives a reset is unknown: none of the shipped code relies on any board register keeping its value. The restart that flips the CPU's byte order asserts this reset: [section 11](#11-across-a-little-endian-restart).

1. Window at `0x1f000000`, 4 MiB; probe word; board revision 2 values from section 4; GE slots 0 to 3 for Elan.
2. HQ2 registers per `registers.toml`, status word with live FIFO count and three finish flags; FIFO line on INT2 local 0 bit 0 from count against `fifo_full`; drain the count as tokens are consumed.

## 10. Boot sequence: what the kernel writes, in order

The Indy and Indigo2 kernels run the same sequence with the differences listed in [ip22-startup.md](ip22-startup.md): two board slots, a per-host reset and retrace-latch clear, a first-board rule for the clock selector, a flat-panel I2C probe, and the same console class table.

The R4000 Indigo kernel's start-up and microcode-load sequence, read from the IRIX 5.3 `IP20boot/gr2.a` (`gr2.o`, `gr2_init.o`, `gr2_tport.o`, `gr2_tpucode.o`; o32 objects) [binary]; each function named below was read in full. The 6.5 objects were compared at `_Gr2HQ2RegInit` (same six stores, same values), `Gr2Start` (same stores) and `gr2_earlyinit` (same order; 6.5 additionally refuses the reuse path when the ready word is 2, which the 5.3 code reaches the same way, because its test is `== 1`). Everything else below that is common to the two is established for 5.3 and **inferred** for 6.5. Offsets are from the graphics window (`0x1f000000`); "register" names are those of [devices/hq2](../../devices/hq2/README.md). The kernel never writes an RE3 or a GE7 register directly: the only GE7 accesses are the probe, the microstore loader and the two program-counter ports; RE3 is written by the microcode alone (the `INIT` token's routine, [devices/re3](../../devices/re3/README.md)). Established [binary] for the absence in these objects.

### A. Per board, at kernel start-up (`gr2_earlyinit`, `gr2.o`)

1. Clear the 60-byte board record; `Gr2Probe` ([section 4](#4-probe-answers-per-indigo-variant)). A failed probe skips the board, and so does a failed `Gr2Init` or `Gr2TpSetup` below.
2. **Reuse test.** If the shared-RAM word `ucode_ready` (`+0x1fffc`) reads 1 *and* this is the first time `gr2_earlyinit` has run since boot, none of steps 3 and 4 runs: the kernel keeps what the board holds, copies the low byte of the shared word `+0x1ffe0` into record byte `0x32`, and only rewrites the cursor image (`initGr2Cursor`, 256 zero bytes at VC1 SRAM `0xa00`, then VC1 registers `0x20` = `0xa00` and three zero half-words). Otherwise steps 3 and 4 run. Established. **Who leaves 1 in the word before the kernel runs: the 4.0.5G PROM.** Its text-port setup (`0xbfc1229c`, the same sequence as the kernel's `Gr2TpSetup`: HQ2 and GE7 console downloads, `gepc` and `unstall` zeroed, the board-class store, a short delay, a blank-screen call) ends with a store of 1 to the word at `0xbfc1237c` (`lui 2`, store at -4), and stores 0 to it on either download failing (`0xbfc122cc`, `0xbfc122f8`). Established [binary], and the IRIX source's PROM library does the same with a named constant for the console-microcode state (`shram[TP_PROBE_ID] = UCODE_TP`, `lib/libsk/graphics/EXPRESS/gr2_init.c`; the diagnostic program stores a different constant when it loads its own images). The 4.0.5D PROM's setup (`0xbfc0f504` to `0xbfc0f588`, INIT store at `0xbfc0f578`) does not write it, and a search of the whole 4.0.5D image for a store of -4 from a `lui 2` base finds none, so a 4.0.5D machine reaches the kernel with whatever the word held, normally 0. Inferred for 4.0.5D (absence by search). So:
   - Boot through the 4.0.5G PROM with the console microcode running: the word is 1 and the kernel takes the reuse path on its first `gr2_earlyinit`. It then needs the board to still hold its console state, and it copies the low byte of `+0x1ffe0` (the RE3 revision, section 4) into the record. A model that boots the real PROM gets this for free if it executes the console tokens and keeps shared RAM.
   - Boot a kernel directly, or through 4.0.5D: start the word at 0. The kernel then resets and re-initialises the board, which is the safe choice and needs no PROM state.
3. `Gr2Reset` (MC `cpuctrl0` bit 10 low, 10 us, high), then `Gr2StartClock` ([devices/clock](../../devices/clock/README.md)), then `Gr2Init`.
4. `Gr2TpSetup(base, width - 1, height - 1, 0)` (section C), which writes the console images and starts them.
5. `Gr2ProbeVC1`: VC1 `addrhi` = 0, `addrlo` = 5, then read `testreg` and keep bits 2:0 as the VC1 revision (record byte `0x33`).
6. Record byte `0x35` = 1 (board live), the board table entry's flag = 1, `dmasync` (`+0x6a050`) = 0; for the first live board only, `htp_register_board(base, gr2_htp_fncs, width, height)` registers the console port between the record store and the last two stores (`gr2.o` `0x100006f4` to `0x10000704`). Established. `Gr2Init` always returns 1 in this object, so its failure branch in step 3 is never taken.

Later, `gr2_init` (after the interrupt system is up): `Gr2RetraceInit`, `setgiovector` for GIO line 0 (`Gr2FIFOInterrupt`) and line 2 (`gr2_retr_intr`), `GfxRegisterBoard`. [section 5](#5-board-outputs-to-int2) has what the lines mean.

### B. `Gr2Init`: `_Gr2RegisterInit`, then `_Gr2HQ2RegInit`

Every step and value is on the chip pages: [vc1-express](../../devices/vc1-express/README.md#initialisation-as-shipped), [xmap5](../../devices/xmap5/README.md#initialisation-as-shipped), [bt457](../../devices/bt457/README.md). Established; the monitor code picks the timing images ([monitor codes](../../devices/vc1-express/README.md#monitor-codes-and-the-kernels-built-in-tables)).

A model's reset values for these registers need not match (software writes them before use); it must accept the writes.

### C. Console images (`Gr2TpSetup`, `gr2_tport.o` and `gr2_tpucode.o`)

1. `Gr2DownloadHQ2` on the kernel's built-in HQ2 console image (129 records, named "IP12/GR2 PROM HQ Microcode"). A failure writes 0 to `ucode_ready` and returns -1.
2. `Gr2DownloadGE7` on the built-in GE7 console image (264 records, "IP12/GR2 PROM GE Microcode"), the same way. Both loaders are on the chip pages: HQ2 first writes the 16-word attribute jump table from image offset `0xfc`, then each record word at `+0x60000 + 4 * address`, and reads every word back; GE7 copies the 512 constants words to shared RAM word 0 and reads them back, clears the microstore, then per record sets `gepc` and writes `+0x683e0`, `+0x683e4`, `+0x683e8`, `+0x683ec` and last `+0x6a064` ([devices/ge7](../../devices/ge7/README.md)). A mismatch makes the loader return failure (and print a line with the verbose flag, which the kernel does not set).
3. `gepc` (`+0x6a070`) = 0, `unstall` (`+0x6a078`) = 0: the GE runs from address 0.
4. The `INIT` token (`+0x40644`) with the **board class** as its operand: 0 for board revisions 1 to 3, 1 for 4, 9, 10 and 11, 2 for 5 to 8 and 12 to 15 (the revision is the inverted low nibble of the byte at `+0x6c000`, [section 4](#4-probe-answers-per-indigo-variant); revision 0 fails `Gr2Probe` and never gets here; the 12-entry jump table is at `gr2_tpucode.o` `0x100001f8`, the selector at `Gr2TpSetup+0x98` to `+0xf4`, and the same mapping is at `Gr2Start` `0x10001a1c` to `0x10001a70` of `gr2.o`, which reads the revision from record byte `0x2e`); then `flushbus` and a 9 us delay. Established for the mapping; the meaning of the class is **inferred** (it selects the back-end variant the microcode drives).
5. `COLOR` (`+0x40648`) = 0, then the `SBOXFI` token (`+0x40654`) with operands 0, 0 (data port), `width - 1`, `height - 1`: a full-screen box in colour 0. `Gr2TpSetup`'s own stores do not poll the FIFO line; the later console calls (`Gr2TpColor`, `Gr2TpDrawBitmap` and the rest) wait for INT2 status byte `0xbfb801c3` bit 0 to clear before each token.
6. `Gr2BlankScreen(base, 0)`: wait up to 10000 x 1 us for XMAP5 chip 0's status bit 0 (`+0x6c11c`) to clear, then for each Bt457 window write address byte 4 and data `0xff` (unblank; the blank case writes 0).
7. `ucode_ready` = 1.

### D. Full images, from user space (`gfxinit`, `Gr2Download`, `Gr2Start`)

`gfxinit` (5.3 `usr/gfx/gfxinit`) maps `hq2.bin`, then `ge7.bin`, from the microcode directory and hands each to the kernel in one request of the form {length, pointer} ([binary], the order is that of the two call sites; the request code `0x6c` is the immediate `li a1,108` before each call, `gfxinit` `0x40a14c` and `0x40a32c`; which library call takes it is not decoded). `Gr2Download` accepts a length above 0 and below `0x100001` (otherwise 0 to `ucode_ready` and EINVAL), maps the user buffer into kernel space (`userdma` and `maputokv`, unmapped again afterwards; nothing is copied, and a failed `userdma` gives EFAULT, `0x10001c90` to `0x10001cb0`), chooses the loader by the magic half-word (`0x965e` HQ2, `0x966e` GE7; anything else prints the magic and returns an error, `gr2.o` `0x10001d58`) and writes 0 to `ucode_ready` when the loader fails. A model must therefore accept a second HQ2 and GE7 load over the running console images with the same register sequence. `Gr2Download` itself makes no reset call, but `Gr2Initialize` (below) does, and the board function table lists Initialize, Download and Start in that order (`gr2.o` `.data` `0x10004b64`): whether the generic graphics layer calls `Gr2Initialize` between the console setup and the downloads was not read (`gfx.o` and `rrm.o` are not read), so a reset between the console images and the full images was **inferred** from that order. Settled for 6.5 by [section 13](#13-what-a-driver-loads-in-order-and-who-loads-what): the 6.5 `gfxinit` issues `GFX_INITIALIZE` before both downloads, and the 6.5 `gfx.o` dispatches that request to the board's `Gr2Initialize`, so the reset is established for 6.5; what it clears stays inferred.

`Gr2Initialize` (`gr2.o` `0x10001afc`) writes, in order: `htp_register_board` with four zero arguments (what that does to the console port is not decoded), `setgiovector` for line 2 to `gr2_retr_intr`, `Gr2Reset`, `Gr2StartClock`, two zero words of kernel data, three timing fields of the board record from record byte `0x2d` (the same lines as in `gr2_init`), then `Gr2Init`, so the six HQ2 stores of B repeat; when record byte `0x38` is non-zero it also calls `ev1_softprobe` and, on a hit, `ev1_reset`. It does not call `Gr2TpSetup` and does not touch `ucode_ready`, so the word still reads 1 after it. The same objects of 6.5 have the same calls in the same order [binary, established for the call list]. Established for 5.3.

`Gr2Start`, run when the graphics system starts, writes: `setgiovector` for line 2 to `Gr2RetraceInterrupt` (the full retrace handler replaces `gr2_retr_intr`), record byte `0x35` = 0, `gepc` = 0, `unstall` = 0, `fin2` = 0, then the board class to the data port `+0x4077c` with no token before it, and waits for status bit 1 (`finflag2`), up to 1,000,000 us, calling `gr2_error` on a timeout whose message is "RE version read back failed" (`gr2.o` `0x100046c8`). Then record byte `0x32` = the low byte of the shared word `+0x1ffe0`, `ucode_ready` = 2 and `Gr2BlankScreen(base, 0)`. Established for the stores, the poll and the message.

The class value is chosen from the board revision (record byte `0x2e`) by a 12-entry table (`gr2.o` `0x10004ab4`, selector `0x10001a1c`): revisions 0 to 3 give 0, 4 and 9 to 11 give 1, 5 to 8 and 12 to 15 give 2. The IRIX source's PROM library has the same mapping for the `INIT` token operand. The Indigo is revision 2, so **the class is always 0**, and a model that sends or expects 0 is right. What the class selects is **inferred**: the back-end variant the microcode drives (video and clock access differ between the Indigo's revision below 4 and the later boards, [devices/clock](../../devices/clock/README.md)); no shipped code or source names the effect, and the 4.0.5D PROM sends 0 without a selection. The 4.0.5G PROM sends 0 for revisions below 4, 1 for 4 and 2 otherwise (`0xbfc12324` to `0xbfc1236c`), a slightly different table that agrees on the Indigo.

What the full image does with it, and what the model must do: the timeout message says the image's first routine reads the RE3's version, so it consumes the class word, reads the render engine's revision, stores it in the low byte of `+0x1ffe0` (the byte gfxinfo decodes as RE3 revision, section 4) and raises finish flag 2. **Inferred** from the message and the kernel's reads; the image's boot routine at GE7 0 was not decoded. A model that does not execute the image must, on the class write, store the RE3 revision byte (4 for rev D) at `+0x1ffe0` and raise `finflag2`. Who else writes `+0x1ffe0` is unknown.

### What a model must provide for this sequence

- Probe answers ([section 4](#4-probe-answers-per-indigo-variant)), the reset ([section 6](#6-what-the-graphics-reset-clears)) and the six HQ2 stores above accepted, a second time as well (`Gr2Initialize`).
- Loaders for both image kinds with read-back, the microstore clear, and `gepc` and `unstall` writes.
- A console `INIT` token that accepts the class operand and a box fill, so the first FIFO words after the download are consumed (the count drains as in [section 1](#what-raises-the-fifo-interrupt-and-how-it-clears)).
- `ucode_ready` as a plain shared-RAM word (0 at power-up, 1 after the console setup, 2 after `Gr2Start`), and the finish flag 2 raised after the class word at start.

## 11. Across a little-endian restart

Asked of the Windigo design (a little-endian NT HAL on the Indigo): does the PROM's console microcode survive the restart that flips the CPU's byte order? Sources: PROM 4.0.5G (read here at `0xbfc003c0` and `0xbfc01390`) and 4.0.5D (the chips repository's PROM page, `0xbfc01320`), the MC specification (rev 1.15, Library `graphics/indy/erikarn-sgi_indy_mc.pdf`, sections 2.9, 5.1, 5.6; banner "SGI Confidential") [public], the IRIX source's PROM graphics library (`stand/arcs/lib/libsk/graphics/EXPRESS/gr2_init.c`) [source], the shipped `sys/mc.h`, and the GR4 board schematic (sheets 7 to 10) [vendor-derived]. Nothing was run.

**What the PROM leaves. Established for 4.0.5G [binary][source]; inferred for 4.0.5D.** 4.0.5G, after a normal boot with graphics as the console: the HQ2 and GE7 console images (149 and 301 records, at `0xbfc4d294` and `0xbfc4e148` in the image; the same sizes as 4.0.5D's) loaded, `gepc` and `unstall` zero, the `INIT` token sent with class 0, VC1, XMAP5, Bt457 and the clock set up by the PROM's own `Gr2Init` equivalent (section 10 and [display](display.md)), and `ucode_ready` (`+0x1fffc`) = 1 (the store of 1 at `0xbfc1237c`, a store of 0 on a failed download at `0xbfc122cc` and `0xbfc122f8`; the image sizes and record checksums re-derived for both console images). 4.0.5D does the same without the `ucode_ready` store: inferred, by the absence of that store in a search of the image (section 10, A.2); the 4.0.5D image was not available for this check. IRIX's reuse test (section 10, A.2) is the only shipped code that relies on this state surviving, and only across a PROM to kernel hand-off with no reset in between.

**The flip asserts the graphics reset. Code established, effect inferred.** The byte-order flip (4.0.5G `0xbfc01390`; 4.0.5D `0xbfc01320` per the chips repository's PROM page, not re-read here) reads the first 16 bits of the CPU configuration EEROM, writes them back with `0x8400` exclusive-ORed in (the two copies of the endian bit, MC specification sections 2.9 and 5.6; the exclusive-OR makes it a toggle) and ends with `lui v0,0xbfa0; lui v1,1; sw v1,(v0)` (`0xbfc013a8` to `0xbfc013b0`): a whole-register store of `0x10000` to CPUCTRL0 at the even-word address, the register's address for a little-endian CPU (the MC answers at both words of each pair, section 5). Its only direct call (searched over the whole image) is `0xbfc003f4`, reached when the CPU's Config register BE bit reads 0 (`0xbfc003e0` to `0xbfc003ec`): the stock PROM runs the flip when it finds the CPU little-endian, to put the machine back to big-endian. Every field but `wr_st` (bit 16) is written zero, including `grr` (bit 10). The MC specification defines `grr` as "clearing this bit will assert reset to the graphics system" and gives it a reset value of 0, its output pin `gio_grxrst_n` as "graphics reset" (section 6.4), and the shipped header names the bit `CPUCTRL0_GRR`, `CONFIG_GRRESET`, which the PROM library and the kernel pulse around a board reset. So from the flip until software next stores a value with bit 10 set, the board is in reset.

`wr_st` does not reset the board itself: the specification calls it a "warm restart" that "starts a R4000 reset sequence without resetting any of the other chips and most of MC" with refresh continuing, and the shipped header says "warm reset without killing memory refresh". Which MC registers a warm restart does reset is not listed, so whether CPUCTRL0 keeps the stored zero in bit 10 is unknown. It does not matter for a stock PROM: the restart runs the PROM from the reset vector, and 4.0.5G's reset entry (`0xbfc00000` jumps to `0xbfc003c0`; nothing branches around the store at `0xbfc0048c`) writes CPUCTRL0 whole with `0x3c002014` ORed with the MUX high-water field (bits 24:20, from the cache line size in Config), so bit 10 is clear again before any graphics code runs. Established for 4.0.5G; 4.0.5D not checked. A stub that stores `0x10400` instead of calling the flip therefore still meets a graphics reset on the way back up. A Windigo layer must release the reset itself, after the PROM or before its own display set-up.

**What a reset costs. Mostly inferred.** Nothing shipped reads anything to see what a reset cleared (section 6), and the PROM library says why it resets (`Gr2Init`: "must reset the graphics board in case ucode is running"). Every shipped path that resets (`gr2_earlyinit`, `Gr2Initialize`, the PROM's graphics check) then reloads the HQ2 and GE7 images, the clock, VC1, XMAP5, the DACs and the six HQ2 registers. That is the software expectation: nothing is assumed to survive. What the hardware keeps is not shown by any shipped code. The GR4 board schematic (Indy Elan Graphics, 21 sheets, GIO64; not the Indigo base board, and topology does not transfer, but the chips are the same) says three things, each read from the page images because the OCR text lost them:

- The HQ2 ASIC's `RESET` pin takes the net `GFX_RST_B_N` (sheet 7), and the GE7 ASIC's `RESET` pin takes `GFX_RST_A_N` (sheet 10). Both nets are made on sheet 2 by gates (U531) from the GIO connector's graphics reset pin `GRX_RST_N` and a board power-up pulse (`PUP020`), so a connector reset or the board's own power-up pulse resets both chips. That the connector pin is the MC's `gio_grxrst_n`, and so `grr`, is inferred from the names and from section 5.1's "assert reset to the graphics system".
- The HQ2 microstore is three 8K by 8 static RAMs on `HQMIC_D<23..0>` and `HQMIC_PC<12..0>` (sheet 8), static RAM with no reset pin, so its contents are not cleared by the reset line itself. The shared data RAM is four 32K by 8 static RAMs (sheet 9). Whether HQ2 or the shared-RAM interface clears either on reset is unknown.
- The GE7 microstore is eight 64K by 16 **dynamic** RAMs (sheet 9). HQ2 drives their row and column strobes, write enable and an 8-bit multiplexed address (sheet 7: `DRAM.AD<7:0>`, `RAS`, `CAS`, `CASIN`, `GWE`; the parts are drawn as `D64Kx16` with row and column strobes on sheet 9, against `S8Kx8` and `SRAM32K8` for the static ones), and the GE7 ASIC has an input pin named `REFRESH` that is wired to the net `GE7STALL` driven by HQ2's `GE7.STALL` (sheets 7 and 10). Reading: HQ2 refreshes the microcode DRAM and stalls the engines while it does, and the HQ2 `refresh` register (`+0x6a080`, 16 in the kernel and both PROMs, 0xf0 in the diagnostic program) sets the interval. Inferred from the net names and the register's name; no shipped code states it. It would also explain why `Gr2DownloadGE7` writes all 65536 microstore words with zeros before loading ("to work around a RAM initialisation problem", the PROM library's comment): the loop touches every row.

Consequence. The reset stays asserted until bit 10 is next set, which in a stock restart is after the PROM has run its own start-up (the MC's cold power-on sequence alone waits about 140 ms, section 2.9; how long the warm restart takes is not stated). If HQ2 keeps refreshing while it is in reset, the DRAM could keep its contents; if refresh waits for the `refresh` write after reset, the GE7 microstore is lost, because DRAM of this size needs refresh within milliseconds (typical for the class, no datasheet for the part is held). Either way a GE7 microstore that survives is not something a driver can know.

## 12. A little-endian CPU on the GIO32 bus

Asked: the byte order of GR2 register and FIFO writes from a little-endian CPU. Sources: the GIO specification, chapters 2 (GIO32) and 4 (GIO64), 6 May 1992 (Library `graphics/indy/erikarn-sgi_indy_gio64.pdf`, "SGI Confidential") [public]; the MC specification (above) [public]; the shipped `sys/mc.h` [binary]; the access widths in sections 1 to 10, [binary].

**The bus carries values, not bytes. Established for the convention, inferred for the MC.**

- The GIO32 bus has 32 address and data lines and no endian signal (the signal table, GIO32 chapter section 2.4, lists AD, AS, READ, MASDLY, SLVDLY, BREQ, BGNT, BPRE, INT, CLK, RESET). The GIO64 bus adds an endian bit to the byte-count cycle; GIO32 has none.
- The specification numbers bytes big-endian on the bus (byte 0 on `AD<31:24>`, Figure 2-1) and says that, because the Indigo can run either way, the bus "supports both little- and big-endian byte numbering schemes", the choice made at power-up from the endianness of the software found on the disk; little-endian puts byte 0 on `AD<7:0>` (Figure 2-2). Devices that talk to the CPU or memory "must always use the alignment described in Figure 2-1 or Figure 2-2". It adds that option cards must therefore run in either mode and that how they learn the mode "is TBD". The only other endian text is the GIO64 chapter's endian bit in the byte-count cycle; nothing found gives a GIO32 card a way to learn the mode.
- The specification's own device-identification rule points the same way: the Product Identification Word "must be done as a word read. (This ensures endian independence.)" (GIO32 chapter section 2.10.1). A GIO32 slave also sees the master starting byte (`AD<31:30>` of the byte-count cycle) and must obey it, and CPU and memory "do not rearrange data"; for a CPU access that field is the address's low bits.
- So a 32-bit load or store, aligned, with byte count 4, puts the register's value on `AD<31:0>` in both modes: byte 0 of the memory image is the register's least significant byte in a little-endian CPU, which is the byte the specification puts on `AD<7:0>` for that mode. A word access is the same wire pattern for both CPUs. Inferred that the MC and MUX chip apply this to a CPU access of a graphics slave (the MC's `big_endian` output pin, section 6.5, follows the `little` bit, section 5.1: "the BIG/LITTLE pin on the MC chip will reflect the value of this register"; and the MC is wired to the low 32 bits of SysAD, section 5); the MC's own registers use the same lane and are simply at the other word of the pair for a little-endian CPU.
- The MC's per-device endian bits (`cpuctrl1` `hpc_fx`, `hpc_little`, `exp0_*`, `exp1_*`) apply to DMA by the HPC and by option cards. The graphics slot has none, and is a slave in any case (chips `platforms/ip20/gio.md`).

**Consequence for the shipped register classes.**

| Class | Offsets | Access the shipped code makes | From a little-endian CPU | Grade |
|---|---|---|---|---|
| Shared RAM, FIFO tokens and data, HQ2 microstore, GE7 slots, HQ2 registers, `finish3` | `+0x0`..`+0x6b004` | 32-bit | Same value, same address. Build floats and packed words by value (shift and OR), not by casting memory; a word of packed bytes is read by the board with byte 0 as the most significant byte, so little-endian memory images of pixels need a byte swap per word | Inferred (word neutrality); packed-byte significance from the Elan TR and the big-endian token catalogue: inferred |
| Board ports, clock, XMAP5 ports, Bt457 ports, VC1 `addrlo`, `addrhi`, `sysctl`, `testreg` | `+0x6c000`..`+0x6c1b4` | byte at the first byte of the word: lane `AD<31:24>` on a big-endian CPU | A byte at the same lane is at address `+3` of the word, because the little-endian CPU numbers bytes the other way. Whether the board then answers depends on whether it decodes the byte address or only the word: **unknown** | Unknown |
| VC1 `command` and `sram` | `+0x6c040`, `+0x6c048` | half-word at the first half of the word (`AD<31:16>`) | Same lane at `+2`; same unknown | Unknown |

Why the narrow case is open: the GIO32 slave sees the address and byte count and nothing about the CPU's order. If the board ignores address bits 1:0 and byte count and drives and takes its byte on the fixed lane (which the NetBSD word-read-and-mask probe and the shipped byte-load probe both fit, as [section 4](#4-probe-answers-per-indigo-variant) notes), the lane-equivalent address (`+3` for a byte, `+2` for a half-word) works. If it applies the big-endian numbering to the byte address and count, a little-endian narrow access never lands on that lane. A word access to a narrow port (`value << 24`, `value << 16`) is the only form that is independent of the answer, but a word store to a port that is also a data port could repeat the effect; no source says. A driver for the first test should use the lane-equivalent narrow address, check the probe word and the board revision read, and fall back to word accesses.

The HPC gives the comparison the Windigo design relies on: the shipped `sys/mc.h` carries a second, little-endian set of MC offsets and the HPC byte registers sit at two addresses naming the same lane, so SGI's own convention for byte-wide devices behind the MC is "same lane, address XOR 3". Nothing equivalent was found for the graphics slot. The IRIX 6.5 base media carry no `sys/gr2hw.h` (the 5.3 and 6.2 discs do; its text was not re-read for a little-endian variant, and the source tree's Express code has none: only the Everest write-gatherer setup says "Big endian", a different host).

#### What the VB-3 and GR-4 port sheets show

Read from the page images of `docs/GR-4_Schematic.pdf` (Indy Elan, sheets 2, 3, 7 and 8) and `docs/VB-3_Schematic.pdf` (Indy XZ video board, sheets 9, 18, 23 and 24); the text layer of both PDFs is unusable. Both are the Indy topology (GIO64, later
video board), not the Indigo's board set, so a sheet fact transfers only as far as the shared chips do. Established [public] for what the sheets draw; the host-address mapping is inferred.

- **Board side of every narrow port is eight bits wide.** The GR4 HQ2 symbol (sheet 7) shows the 32 GIO data pins and, separately, a display-bus group: eight data pins `DISP/VID.00` to `.07`, four address pins `DISPADR.00` to `.03`, `DISP.CS`, `DISP.R/W` and three command pins `DISPCMD.00` to `.02`.
  The VB-3 devices hang on that bus: the XMAP symbol (sheet 9, labelled **XMAP7**, a later part than this board set's XMAP5) has `DBUS.0` to `.7`, `CMD.0` to `.2`, two strobes and R/W; the VC1 (sheet 18) has `HDATA.0` to `.7`, `CMD.0` to `.2`, `CS` and R/W. So data crosses in bytes, a device is chosen by a 4-bit number and a register inside it by a 3-bit number.
- **The device decode (VB-3 sheet 23, two 74FCT138 decoders enabled by `DISP_CS_N`, selected by `DISP_A<3>`):** with `DISP_A<3:0>` = 0 the version port, 1 the clock, 2 the VC1, 3 and 4 the Bt479 read and write strobes, 5, 6 and 7 the red, green and blue Bt457; 8 to 12 the XMAP chips 0 to 4, 13 all five XMAPs together, 14 and 15 two stereo write strobes.
  Inferred: `DISP_A<3:0>` is host address bits 8:5 and `DISPCMD<2:0>` bits 4:2, because the offsets the Indigo software uses fit exactly: version at `+0x6c000`, VC1 `+0x6c040`, Bt457 `+0x6c0a0`, `+0x6c0c0`, `+0x6c0e0`, XMAP chip n at `+0x6c100 + 0x20 * n`, the broadcast window `+0x6c1a0`, all `0x6c000 + 0x20 * device`, and each XMAP's eight ports are the 3-bit register select (window offsets `0` to `0x1c`).
- **No lane logic outside the HQ2.** GR4 sheet 3 carries `GIO_AD<31:0>` to the HQ2's `GIO.00` to `.31` through two registered 16-bit transceivers bit for bit (`GIO_AD<n>` to `PG_AD<n>`), with no byte permutation, and the HQ2 symbol has no byte-count, address or endian pin. Which of the 32 lines the HQ2 samples or drives for the eight display-bus data bits, and
  how a halfword or word store to a port becomes byte cycles, is therefore inside the HQ2 and on no sheet read. The XZ board's XMAP writes pass through two 9-bit FIFOs (sheet 24: one for the command and R/W bits, one for the data byte) before they reach the chips, so a word store to the XMAP `mode` port must be serialised into byte writes (inferred); the order is not drawn.
- **The version read** (GR4 sheet 8, two 74FCT257 multiplexers selected by `DISP_CMD0`, enabled on a read of device 0): with `DISP_CMD0` = 0, data bits 3:0 are the four jumper-strapped `GR_VERSION_N` lines and bits 7:4 the `MONTYPE_N` lines; with it = 1, bit 0 is `VB3_IN0_N`, bit 1 `VB3_IN1_N`, bit 4 `VM24_IN`, bit 5 `ZB_IN` and bits 2, 3, 6 and 7 a pulled-down net. That is the Indy's assignment, not the Indigo's port 0 to 3 ([section 4](#4-probe-answers-per-indigo-variant)); only the eight-bit width and the single-lane output carry over.

Answer to the byte-lane question: **not settled by these sheets.** They show an eight-bit path behind the HQ2 and a lane-neutral GIO connection to it, so the lane choice is the HQ2's. What would settle it: the Indigo's own Express board set (not held), the HQ2's internal logic, or a read of a port from a little-endian CPU (not permitted).
Until then the advice above stands: use the lane-equivalent narrow address, check the probe word, and fall back to word stores of the shifted value.

**Image files.** `hq2.bin`, `ge7.bin` and the `.u` timing files are big-endian structures read as half-words, composed by the loaders as `(first << 16) | second` (the PROM library's loaders do this on every record word; the same fields in [devices/ge7](../../devices/ge7/README.md#microcode-image-format)). A little-endian loader must read each half-word big-endian and store the composed 32-bit value; copying the file's words with a little-endian load is wrong.

**Pixel and image DMA.** The MC graphics DMA engine's change log adds a "little bit" to the DMA descriptors (MC spec revision history, February 1991); no register or field of it is described in the specification or in the shipped header (the header's `gdmada_t` has only a `_MIPSEL` field order for the stride and line count). Whether the engine swaps bytes for a little-endian host is unknown. By the value rule above, a memory image moved by the engine arrives as the same 32-bit words the CPU sees, so packed formats need the per-word swap in software or the engine's bit, and it cannot be told which from the held sources.

Checked and found silent: the Virtual DMA Specification, draft 1.5 of 13 February 1992 (Library `graphics/indy/erikarn-sgi_indy_vdma.pdf`), has no endian text. The R3000 Indigo base board (HP-1 schematic, sheet 22, `74FCT652` transceivers) carries `GIO.BUS` bits 0 to 31 straight through to the backplane with no byte permutation, so any lane logic is on the MC side or the graphics board; the R4000 Indigo's base board is not in the Library.

Settled by: a board with a little-endian CPU (not permitted); the GR2 board's byte-lane wiring (the VB-3 and GR-4 schematics' port sheets, not traced for this, and the Indigo's own board set); a `gr2hw.h` or driver variant for a little-endian host (none found); the MC Virtual DMA Programmer's Guide (a different document from the specification above; not held).

## 13. What a driver loads, in order, and who loads what

The order the shipped system does it, for the Indigo (board class 0). Steps 1 to 4 are the kernel's start-up and are section 10 in full; a replacement driver that wants a text console without the full images stops after step 4. Grades: the kernel and PROM steps are established (section 10); the 6.5 `gfxinit` rows are established from its disassembly (below); the X server rows are inferred from the m2c output in `gr2_ddx/decomp`, not re-read against the machine code.

| # | Step | Who | What |
|---|---|---|---|
| 1 | Release the graphics reset | PROM; kernel `Gr2Reset`; a driver after a restart | MC CPUCTRL0 bit 10 low 10 microseconds, then high ([section 11](#11-across-a-little-endian-restart) for the restart case) |
| 2 | Clock | `Gr2StartClock` | the 17-byte table or the 7-byte sets ([devices/clock](../../devices/clock/README.md)) |
| 3 | Back end | `_Gr2RegisterInit` | INT2 retrace latch, three Bt457 windows, VC1 timing images (built in for monitor codes other than 6 and 14; the `.u` files carry the same two sets), display-ID tables, VC1 registers, cursor image, `sysctl`, XMAP5 three passes, the six HQ2 registers ([sections 6 and 10 B](#b-gr2init-_gr2registerinit-then-_gr2hq2reginit)) |
| 4 | Console microcode | `Gr2TpSetup` (kernel built-in pair; the PROM's own pair) | HQ2 image, then GE7 image (loader order of section 10 C), `gepc` = 0, `unstall` = 0, `INIT` token (`+0x40644`) with the class, box fill, unblank, `ucode_ready` = 1 |
| 5 | Reset again, then register init again | `GFX_INITIALIZE` (`Gr2Initialize`), issued by `gfxinit` | `Gr2Reset`, `Gr2StartClock`, `Gr2Init`; it does not call `Gr2TpSetup`. The dispatch is read: in `gfx.o` the request `0x6a` calls entry 3 of the board's function table (`0xc` bytes in; `0x2c9c` to `0x3068`), and `gr2.o`'s table puts `Gr2Initialize` at entry 3 (`.data` `0x44`; `Gr2Download` at 4 for `0x6c`, `gfx.o` `0x2ff8` and `0x31fc`; `Gr2Start` at 5 for `0x6b`, `0x30f0`), in the order of the shipped `sys/gfx.h` (`gf_Initialize`, `gf_Download`, `gf_Start`). The console microcode is gone by inference (a reset just ran) and what `htp_register_board` with zero arguments does to the console port is not decoded |
| 6 | Full HQ2 image | `gfxinit`, `GFX_DOWNLOAD` (`0x6c`) | `hq2.bin` mapped read-only, `{length, pointer}` handed to the kernel, which loads it through the HQ2 loader |
| 7 | Full GE7 image | `gfxinit`, `GFX_DOWNLOAD` | `ge7.bin`, the same way |
| 8 | Start | `GFX_START` (`Gr2Start`) | `gepc` = 0, `unstall` = 0, `fin2` = 0, class word to `+0x4077c`, wait for `finflag2`, RE3 revision from `+0x1ffe0`, `ucode_ready` = 2, unblank |
| 9 | Screen set-up | X server (`gr2.so`) | full-image tokens to clear planes (`expInitHW`: slots at `+0x404b0`, `+0x4052c`, `+0x404d4`, `+0x40530`, `+0x40540`, `+0x404c0` with data at `+0x4077c`), VC1 display-ID tables at SRAM `0x1400` and `0xb00` and registers `0x40`, `0x42`, `0x44` = `0xff04`, `0x60`, `sysctl` = `0x3c` (`expvc1Init`), cursor, XMAP5 mode and colour-table writes through `+0x6c1a8`, `+0x6c1b0` and `+0x6c1b4` with a poll of `+0x6c11c` bit 1; timing files and genlock adjusters through `setmon` |

**What the 6.5 `gfxinit` does** (`usr/gfx/gfxinit`, n32, SHA-256 `844c396b...a56a13b`; `gr2_init` at `0x10007c50`, read to its normal return at `0x10007ea4`, the error branches not read). The board table in its data has four entries, `GR2`, `GR2EV`, `GR2TP` and `GR2SH`, each with an init hook (`gr2_init` for all four), an info function (`gr2_info` for the first, `gr2ev_info` for the rest) and two further hooks that are null in all four. The per-board loop issues `GFX_ATTACH_BOARD` (103), `GFX_MAPALL` (110), the null map hook, `GFX_INITIALIZE` (106), the init hook, `GFX_START` (107), the null post-start hook and `GFX_DETACH_BOARD` (104). The ioctl numbers are the shipped `sys/gfx.h`'s `GFX_BASE` (100) plus 1 to 13; `GFX_DOWNLOAD` is 108 = `0x6c`, the request code that section 10 D read as an immediate in the 5.3 binary, and the message "GFX_DOWNLOAD failed" confirms the name. `gr2_init` builds `<ucode_dir>hq2.bin`, then `<ucode_dir>ge7.bin` (strings `hq2.bin` and `ge7.bin` in the read-only data), opens, `fstat`s and maps each, closes it, prints "Loading HQ2 ucode from %s" (and GE7) when verbose, and issues the ioctl on the board's device descriptor with a two-word argument, the file size from `fstat` (inferred) then the mapped pointer, HQ2 first. Afterwards, when byte `0x38` of its second argument is positive, it calls a function (`0x10007c48`) and, if that answers, prints a message; purpose not read. The generic `gfx_download_args` has more fields (`magic`, `unit`, `off`, `width`, `entry`, `run`); `gr2_init` does not set them, which fits the kernel telling the images apart by the file's own magic. `gfxinit` is run by the shell script `usr/bin/X11/X` (SHA-256 `26360a4c...105225f`) before it execs `Xsgi`, and `startgfx` only starts `xdm`, and a search of `etc`, `usr/bin`, `usr/sbin`, `usr/lib/X11` and `var/X11` on the base media finds no other caller (one Origin start script mentions it), so on this release steps 5 to 8 happen when X starts.

**Files on the 6.5 media** (all under `usr/gfx`, identical to the 6.5 hashes of [section 8](#8-microcode-image-checksums)):

| File | Role | Loaded by |
|---|---|---|
| `ucode/hq2.bin`, `ucode/ge7.bin` | full images | `gfxinit` |
| `ucode/GR2/vof/{30hz,48hz,50hz,60hz,72hz,ccir50,ccir60,iris3k,ntsc,pal,presenter,presenter1280,rs343a,st492}.u` and the link `48.u` | VC1 timing files, 2176 bytes ([devices/vc1-express](../../devices/vc1-express/README.md#timing-image-format)) | `setmon` (its string `/usr/gfx/ucode/GR2/vof/%s`; the ioctl it uses is `Gr2SetMonitor`'s, not traced); 60 and 72 Hz are also built into the kernel |
| `ucode/GR2/vof/adjntsc.bin`, `adjpal.bin` | genlock adjustment | `setmon` (`setAdjGenlock` in its symbols); not decoded |
| `arch/IP12GR2*/libGLcore.so` | GL core, writes tokens by CPU store | the GL client, after step 8 |

The kernel's built-in console images, the PROM's console images and the full images are three different microcode builds ([section 8](#8-microcode-image-checksums), [microcode](microcode.md#the-console-tokens)): the full `hq2.bin` has no word for `RECTCOPY` (slot 409, `+0x40664`) or for `FINISH` (403), so a driver that draws the text console with the rectangle-copy token needs a console image, not the full one. 4.0.5G's console images are cut with `tools/ucode-decode.py cut` at `0x4d294` (HQ2, SHA-256 `1f79a4dc...74e8f`) and `0x4e148` (GE7, `eede51f1...4e188`); both pass the record checksums (149 and 301 records, same sizes as 4.0.5D's). The kernel's built-in pair has 129 and 264 records, a different build; which tokens it carries was not checked. A driver cannot ship either; it would read them from the user's own PROM (offsets above, PROM identified by SHA-256) or media.

**What the kernel and the X server do not load.** The RE3 and the GE7 registers are never written by the kernel or the PROM; microcode writes them. The kernel loads no timing file other than its two built-in sets; a mode other than 60 or 72 Hz reaches VC1 only through `Gr2SetMonitor` from user space. Neither loads genlock data without `setmon`. Open: the 6.5 kernel's own copy of the console pair against the PROM's, `Gr2SetMonitor`'s ioctl number, and the X server's XMAP5 mode-table writes against its machine code.
